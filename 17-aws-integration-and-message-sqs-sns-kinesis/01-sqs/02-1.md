# Part 1 — Why Do We Need SQS?

Imagine an online shopping website.

```
Customer

    │

    ▼

Place Order

    │

    ▼

Order Service

    │

    ▼

Database
```

Normally this works perfectly.

---

## Suddenly...

Black Friday arrives.

Instead of

```
10 orders/minute
```

You receive

```
100,000 orders/minute
```

What happens?

```
Customer

     │

100,000 Requests

     │

     ▼

Order Service

     │

     ▼

Database
```

The database cannot process all requests.

Result:

- ❌ Slow website
- ❌ Database overload
- ❌ Orders lost
- ❌ Application crash

---

AWS solution:

# Amazon SQS

Instead of sending directly to the database,

put orders into a queue.

```
Customers

      │

Place Order

      │

      ▼

Amazon SQS Queue

      │

      ▼

Order Processor

      │

      ▼

Database
```

Now,

Customers can continue placing orders.

The database processes them one by one.

Nothing is lost.

---

# Real-Life Analogy

Imagine a bank.

Without Queue

```
100 customers

↓

Everyone runs to one cashier

↓

Chaos
```

With Queue

```
100 customers

↓

Queue

↓

Cashier serves

1

2

3

4

...
```

Exactly how SQS works.

---

# What is SQS?

SQS

=

Simple Queue Service.

It is

> A fully managed message queue.
> 

It stores messages until another application processes them.

It **does NOT process messages**.

It only stores them safely.

---

# SQS Architecture

```
Producer

      │

Send Message

      ▼

──────────────

Amazon SQS

──────────────

      │

Poll Message

      ▼

Consumer

      │

Delete Message
```

Three components

- Producer
- Queue
- Consumer

---

# Producer

Producer

=

Application sending messages.

Example

Shopping website.

When customer places an order

↓

Producer sends

```
{
 "OrderID":1001,
 "Customer":"John",
 "Amount":200
}
```

to SQS.

Producer finishes immediately.

It doesn't wait.

---

# Consumer

Consumer

=

Application reading messages.

Example

```
Order Processing Service
```

Consumer

polls

SQS

gets message

processes order

deletes message.

---

# Important Point

Producer

and

Consumer

never talk directly.

```
Producer

↓

Queue

↓

Consumer
```

This is called

**Decoupling**.

---

# What is Decoupling?

Without SQS

```
Order Service

↓

Shipping Service

↓

Inventory

↓

Email

↓

Payment
```

Every service depends on another.

If Shipping fails

↓

Everything fails.

---

With SQS

```
Order Service

↓

Queue

↓

Shipping

↓

Queue

↓

Email

↓

Queue

↓

Inventory
```

Each service works independently.

Huge exam point.

---

# Standard Queue

This is the default SQS.

AWS recommends Standard Queue unless ordering matters.

---

Characteristics

## Unlimited Throughput

No practical limit.

Millions of messages.

---

## Unlimited Messages

Queue never becomes "full."

---

## Retention

Default

```
4 Days
```

Maximum

```
14 Days
```

If consumer never reads

↓

Message stays.

After retention

↓

Deleted automatically.

---

Example

Monday

Producer sends message.

Consumer crashes.

Wednesday

Consumer starts.

Message still exists.

---

# Message Size

Maximum

```
256 KB
```

Need larger payload?

Store file in S3.

Put S3 URL inside SQS.

Huge exam trick.

---

Example

Instead of

```
100MB Video
```

Do

```
Video

↓

S3

↓

URL

↓

SQS
```

# At-Least-Once Delivery

Very important.

AWS promises

Message

will arrive

AT LEAST

once.

Sometimes

Twice.

Example

```
Order 1001

↓

Consumer

↓

Network problem

↓

AWS thinks

Consumer didn't receive it

↓

Send again
```

Duplicate.

Applications must handle duplicates.

may arrive
