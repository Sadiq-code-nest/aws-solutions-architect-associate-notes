# A1

## 1. ✅ Correct Answer

### **Option 1 — Create one Amazon SNS topic and use SNS subscription filter policies to route messages to the appropriate SQS queue.** ✅

This is the best solution because the requirement is:

> **One type of quote → one specific SQS queue**
> 

SNS can publish the message once to a topic, and **subscription filter policies** determine which subscribed SQS queue should receive it.

```
                         ┌──→ SQS Queue A → Quote Type A
                         │
Application → SNS Topic ─┼──→ SQS Queue B → Quote Type B
                         │
                         └──→ SQS Queue C → Quote Type C

                    SNS subscription
                    filter policies
```

For example:

```
Message:
quoteType = "AUTO"
        ↓
SNS Topic
        ↓
Filter policy on Auto Queue = AUTO
        ↓
Auto SQS Queue ✅
```

The other queues don't receive the message.

### Why this is cost-effective

You don't need to:

- create many SNS topics,
- send the same message to every SQS queue,
- build custom filtering logic,
- introduce Kinesis.

**One SNS topic + multiple filtered SQS subscriptions** is the clean fan-out/filtering architecture.

# 2. 🧠 Core Concept — Very Simple

### Translation:

> **"I have different types of messages and want each type to automatically go into its own SQS queue."**
> 

The AWS pattern is:

> **SNS = distribute/filter messages → SQS = store messages for consumers**
> 

```
                SNS
                 ↓
       ┌─────────┼─────────┐
       ↓         ↓         ↓
     Queue A   Queue B   Queue C
      Type A    Type B    Type C
```

The important feature is **SNS subscription filtering**.

```
Application
    ↓
SNS Topic
```

The application doesn't need to know about every individual queue.

---

### Step 2 — Subscribe each SQS queue

Suppose there are three quote types:

```
AUTO
HOME
LIFE
```

Create:

```
SNS Topic
   │
   ├── Auto SQS Queue
   ├── Home SQS Queue
   └── Life SQS Queue
```

---

### Step 3 — Apply subscription filter policies

For example:

```
Auto Queue:
quoteType = AUTO

Home Queue:
quoteType = HOME

Life Queue:
quoteType = LIFE
```

Now SNS evaluates the message attributes against each subscription.

```
Message
quoteType = HOME
      ↓
   SNS Topic
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
Auto Home Life
 ❌    ✅    ❌
```

That's exactly what the requirement asks for.

---

### What about the 24-hour requirement?

The question says:

> **"The entire message processing should not exceed 24 hours."**
> 

This is important because SQS provides configurable **message retention**.

If messages must remain available for up to 24 hours, configure the queue retention period accordingly.

The architecture itself doesn't require a special 24-hour service.

# 4. ❌ Why Every Other Option Is Wrong

## Option 2 — Publish the same messages to all SQS queues and filter inside each queue ❌

This is inefficient.

The architecture would be:

```
                SNS
                 ↓
       ┌─────────┼─────────┐
       ↓         ↓         ↓
     Queue A   Queue B   Queue C
       ↓         ↓         ↓
     Filter    Filter    Filter
```

Every queue receives **every message**.

Then each queue has to determine:

> "Is this message actually for me?"
> 

For example:

```
AUTO message
   ↓
SNS
   ↓
┌───────┬───────┬───────┐
↓       ↓       ↓
Auto    Home    Life
Queue   Queue   Queue
↓       ↓       ↓
✅      ❌       ❌
```

You're unnecessarily delivering the message to multiple queues.

### Why Option 1 is better

Option 1 filters **before delivery**:

```
SNS
 ↓
Filter
 ↓
Only designated queue
```

Option 2 filters **after delivery**:

```
SNS
 ↓
All queues
 ↓
Filter
```

Therefore Option 2 creates unnecessary message traffic and processing.

---

## Option 3 — Kinesis Data Streams + Kinesis Client Library ❌

Kinesis Data Streams is designed for **high-throughput streaming data**.

```
Producers
    ↓
Kinesis Data Streams
    ↓
Consumers
```

You could technically build custom logic to inspect records and send them to different SQS queues.

But that means you're introducing unnecessary components:

```
Kinesis
   ↓
KCL application
   ↓
Custom routing logic
   ↓
SQS queues
```

The question doesn't require:

- stream processing,
- ordered shards,
- replaying stream records,
- high-throughput event streaming.

It simply requires:

> **Message filtering and routing to different queues.**
> 

SNS subscription filtering solves that directly.

### Exam lesson

> **Don't introduce Kinesis when SNS + SQS already solves simple message distribution/filtering.**
> 

---

## Option 4 — Multiple SNS topics ❌

You could create:

```
SNS Auto Topic → Auto Queue
SNS Home Topic → Home Queue
SNS Life Topic → Life Queue
```

But that's unnecessarily complicated.

Instead:

```
             One SNS Topic
                  ↓
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Auto       Home      Life
      Queue      Queue     Queue
```

SNS subscription filter policies allow one topic to handle different message types.

Therefore, multiple topics create additional management overhead without providing a benefit required by the question.

# 7. 🏢 Easy Real-World Example

Imagine an insurance company receives three types of quote requests:

```
AUTO
HOME
LIFE
```

Without SNS filtering:

```
                  SNS
                   ↓
          ┌────────┼────────┐
          ↓        ↓        ↓
        Auto      Home      Life
        Queue     Queue     Queue
          ↓        ↓        ↓
        Filter   Filter   Filter
```

Every queue receives every message.

### Better architecture

```
                  SNS
                   ↓
          Subscription filters
             /       |       \
            ↓        ↓        ↓
         AUTO      HOME      LIFE
           ↓         ↓         ↓
       Auto SQS   Home SQS   Life SQS
```

Suppose the application publishes:

```
{
    "quoteType": "HOME",
    "customer": "123"
}
```

SNS checks the subscriptions:

```
AUTO Queue filter → HOME ≠ AUTO → ❌
HOME Queue filter → HOME = HOME → ✅
LIFE Queue filter → HOME ≠ LIFE → ❌
```

Only the **Home SQS queue** gets the message.

## ⭐ Important distinction

| Requirement | Best service/pattern |
| --- | --- |
| **Filter messages by attributes and route to specific queues** | 🟢 **SNS subscription filter policies → SQS** |
| **Fan out the same message to multiple consumers** | 🟢 **SNS → SQS** |
| **Queue messages for asynchronous processing** | 🔵 **SQS** |
| **High-throughput streaming + replay** | 🟠 **Kinesis Data Streams** |
| **Custom stream processing/routing** | 🟠 **KCL + Kinesis** |
| **Separate topics for unrelated notification domains** | 🟡 **Multiple SNS topics** |

### The most important distinction:

```
                 SNS
                  │
        Does every subscriber
          need the message?
             /         \
           YES         NO
            ↓           ↓
       Normal SNS    Filter Policy
                        ↓
                  Specific SQS
```
