# 1. Visibility Timeout (Default = 30 sec)

## What problem does it solve?

Suppose there are **3 chefs**.

One order arrives.

```
Queue

Order #101
```

Chef A picks it.

Without visibility timeout...

```
Chef A  ---> Order #101

Chef B  ---> Order #101

Chef C  ---> Order #101
```

Everyone cooks the same burger.

Customer receives

🍔🍔🍔

Three burgers.

Wrong.

---

## AWS Solution

When Chef A picks the order,

AWS hides it.

```
Queue

Order #101

↓

Chef A receives it

↓

Message becomes invisible
for 30 seconds
```

Now

Chef B checks the queue.

```
Nothing here.
```

Chef C checks.

```
Nothing here.
```

Only Chef A can process it.

---

## Scenario 1 (Processing completed)

```
12:00:00

Chef A receives Order #101

↓

12:00:10

Burger finished

↓

DeleteMessage

↓

Message removed forever
```

Everything is perfect.

---

## Scenario 2 (Chef crashed)

```
12:00:00

Chef A gets message

↓

Starts cooking

↓

Computer crashes

↓

Never deletes message
```

AWS waits

30 seconds.

```
12:00:30

Visibility Timeout ends

↓

Message becomes visible again

↓

Chef B gets it

↓

Processes it
```

Nothing is lost.

---

## What if the timeout is too short?

Your application needs

60 seconds.

Visibility Timeout

30 seconds.

Timeline

```
12:00:00

Chef A receives order

↓

Still cooking...

↓

12:00:30

Timeout expired

↓

Chef B also receives it

↓

Now TWO chefs cook
the same order
```

Duplicate processing.

---

## What if timeout is too long?

Suppose

Visibility Timeout

5 hours.

Chef crashes after

10 seconds.

AWS waits

5 hours

before retrying.

```
Customer waits

5 HOURS
```

Terrible.

---

## Rule

Set

Visibility Timeout

slightly longer than processing time.

Example

```
Average Processing

20 seconds

↓

Visibility Timeout

30-60 seconds
```

---

# Summary

```
Visibility Timeout

=

Hide the message

while someone is working on it.
```

# 3. Delivery Delay (Default = 0 sec)

This is different.

Many students confuse it with Visibility Timeout.

They are NOT the same.

---

## Delivery Delay

Means

Producer sends message

BUT

SQS waits

before showing it.

---

Example

Customer places pizza order.

Restaurant policy:

```
Wait

5 minutes

before cooking

because

customer may cancel.
```

Timeline

```
12:00

Order sent

↓

12:00-12:05

Nobody can even see it

↓

12:05

Message appears

↓

Chef starts cooking
```

---

Notice

Nobody has picked it yet.

AWS is simply waiting.

---

Diagram

```
Producer

↓

Send Order

↓

SQS

(Hidden)

↓

5 Minutes

↓

Visible

↓

Consumer
```

---

## Difference

Visibility Timeout

↓

Consumer already has message.

Delivery Delay

↓

Consumer cannot even see message yet.

---

# Summary

```
Delivery Delay

=

Wait before making the message available.
```

# 5. Receive Message Wait Time (**Long Polling**)

Imagine

Chef keeps checking.

```
Order?

No.

Order?

No.

Order?

No.

Order?

No.

Order?

No.
```

Every second.

Waste.

---

Default

0 seconds.

Meaning

```
Ask

↓

No message

↓

Leave

↓

Ask again
```

Millions of API calls.

Higher cost.

---

Set

20 seconds.

Now

Chef asks once.

```
Any order?

↓

I'll wait

20 seconds.
```

If order arrives after

8 seconds

AWS immediately returns it.

No need to ask again.

---

Timeline

```
12:00:00

Consumer asks

↓

Wait

↓

12:00:08

Message arrives

↓

Immediately returned
```

---

Much fewer API calls.

Much cheaper.

AWS recommends

20 seconds.

---

# Summary

```
Receive Message Wait Time

=

How long the consumer waits

for a message before giving up.
```

# Complete Comparison Table

| Setting | Default | What It Controls | Real-Life Example | If Too Low | If Too High |
| --- | --- | --- | --- | --- | --- |
| **Visibility Timeout** | 30 sec | How long a received message is hidden from other consumers | Chef is cooking; no other chef should take the same order | Duplicate processing if work isn't finished | Slow recovery if the consumer crashes |
| **Message Retention** | 4 days | How long an unprocessed message stays in the queue | Restaurant keeps old order tickets for a few days | Messages may be deleted before recovery | Old messages stay longer (more storage cost) |
| **Delivery Delay** | 0 sec | Delay before a new message becomes visible | Wait 5 minutes before starting to prepare food | Usually no issue | Jobs start later than intended |
| **Maximum Message Size** | 256 KB | Largest allowed message | Order details fit; video file doesn't | Can't send larger payloads | Cannot exceed 256 KB (hard AWS limit) |
| **Receive Message Wait Time** | 0 sec | How long a consumer waits for a message (long polling) | Chef waits up to 20 seconds for a new order instead of checking every second | More API calls and higher cost | Consumer may wait longer before an empty response (usually acceptable) |

# 🎯 One Sentence to Remember Each Setting

- **Visibility Timeout** → *"I picked the message—hide it from everyone else while I work."*
- **Message Retention** → *"If nobody processes the message, how long should AWS keep it?"*
- **Delivery Delay** → *"Don't show this new message yet; wait first."*
- **Maximum Message Size** → *"How much data can fit inside one SQS message?"*
- **Receive Message Wait Time** → *"If the queue is empty, how long should the consumer wait before trying again?"*

## The Most Common Exam Confusion

Many students confuse **Visibility Timeout** and **Delivery Delay**. The key difference is:

```
Delivery Delay
──────────────
Producer sends message
        │
        ▼
Message is NOT visible to anyone yet
        │
        ▼
Delay expires
        │
        ▼
Consumer can now receive it

Visibility Timeout
──────────────────
Consumer already received the message
        │
        ▼
Message becomes hidden from OTHER consumers
        │
        ▼
Consumer finishes and deletes it
(or timeout expires and it becomes visible again)
```

**Easy memory trick:**

- **Delivery Delay = Before anyone can see the message.**
- **Visibility Timeout = After one consumer has already taken the message.**
