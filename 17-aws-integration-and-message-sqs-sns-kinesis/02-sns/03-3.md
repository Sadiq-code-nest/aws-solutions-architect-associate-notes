# 3

This topic is the **next level of SNS** and is asked frequently in **AWS SAA-C03**.

Students usually understand **SNS** and **SQS** individually, but the confusion starts when AWS combines them.

The most important concept to remember is:

> **SNS broadcasts events, SQS stores work.**
> 
> 
> When you combine them, you get **broadcast + reliability + scalability**.
> 

Let's build the concept from scratch.

---

# Part 1: Why SNS + SQS Together?

Suppose you built an Amazon-like shopping website.

When a customer places an order, many services must react.

```
Customer

↓

Buying Service

↓

Order Created
```

Now who needs this event?

- Shipping Service
- Fraud Detection
- Analytics
- Inventory
- Email
- Billing

Without SNS:

```
Buying Service

├── Shipping
├── Fraud
├── Inventory
├── Billing
├── Analytics
└── Email
```

Problems:

- Too many direct connections
- One service failure affects others
- Hard to add new services

---

## Solution

```
Buying Service

↓

SNS Topic

↓

Everyone gets notified
```

Easy.

But...

Another problem appears.

---

# Problem with SNS Alone

Suppose Shipping Server is down.

```
Buying Service

↓

SNS

↓

Shipping ❌ Down
```

SNS immediately pushes the notification.

If Shipping is unavailable...

👉 The notification may be missed.

SNS is **Push**, not long-term storage.

---

AWS Solution

Combine SNS with SQS.

---

# SNS + SQS Fan-Out

```
                    Publish

Buying Service
      │
      ▼
+----------------+
|   SNS Topic    |
+----------------+
     │        │
     │        │
     ▼        ▼
+---------+ +---------+
| SQS #1  | | SQS #2  |
+---------+ +---------+
     │           │
     ▼           ▼
Shipping      Fraud
Service       Service
```

This architecture is called

# Fan-Out Pattern

One message

↓

Many queues

↓

Each queue has its own consumer.

---

# Step-by-Step Example

Customer buys an iPhone.

Buying Service publishes

```
Order ID : 1001
Product : iPhone
Customer : John
```

to SNS.

SNS immediately copies the message.

```
SNS

↓

Shipping Queue

↓

Fraud Queue

↓

Inventory Queue

↓

Analytics Queue
```

Each queue now stores its own copy.

Shipping processes whenever ready.

Fraud processes whenever ready.

Inventory processes whenever ready.

No one affects anyone else.

---

# Why Not Connect SNS Directly?

Without SQS

```

```

---

With SQS

```

↓

↓

```

No data loss.

# Why SQS Makes It Better

Each queue provides

### Message Persistence

Stores messages until processed.

```
SNS

↓

SQS

↓

Wait...

↓

Consumer starts

↓

Reads message
```

---

### Retry

Consumer crashes?

```
Read Message

↓

Crash

↓

Visibility Timeout expires

↓

Message becomes visible

↓

Another consumer retries
```

Nothing lost.

---

### Independent Scaling

Shipping gets busy?

Increase Shipping workers.

Fraud gets busy?

Increase Fraud workers.

No interference.

```

↓

20 EC2 instances

Fraud Queue

↓

5 EC2 instances
```

Each scales independently.

# Important Permission

SNS **cannot automatically write into SQS**.

SQS must allow it.

Think of SQS saying

> "I allow SNS Topic XYZ to send messages."
> 

This is done using an **SQS Queue Policy**.

Without it

```
SNS

↓

Access Denied
```

# SNS Message Filtering

This is another favorite exam topic.

Normally

SNS sends every message to every subscriber.

Example

```
Order Placed

↓

Queue1

Queue2

Queue3
```

Even if Queue2 doesn't care.

Wasteful.

---

AWS Solution

Subscription Filter Policy.

Each subscriber says

"I only want certain messages."

---

Example

SNS receives

```
{
 State : Placed
}
```

Subscribers

```
Placed Queue

Cancelled Queue

Declined Queue
```

Filter

Placed Queue

```
State = Placed
```

Cancelled Queue

```
State = Cancelled
```

Declined Queue

```
State = Declined
```

SNS publishes

```
State = Placed
```

Result

```
Placed Queue ✔

Cancelled Queue ✖

Declined Queue ✖
```

Only one queue receives it.

---

Another example

Product Categories

SNS receives

```
Product = Laptop
```

Subscribers

```
Laptop Queue

Phone Queue

TV Queue
```

Only Laptop Queue gets it.

---

Another example

Order Status

SNS receives

```
Status = Delivered
```

Subscribers

```
Placed Queue

Delivered Queue

Cancelled Queue
```

Only Delivered Queue receives it.

# Exam Cheat Sheet

| Requirement | Service/Feature |
| --- | --- |
| One event → Many applications | SNS Fan-Out |
| Reliable delivery to each application | SNS + SQS |
| Add new subscribers without changing publisher | SNS Fan-Out |
| One S3 event → Multiple SQS queues | S3 → SNS → SQS |
| Need ordering | SNS FIFO |
| Need ordering + no duplicates | SNS FIFO + SQS FIFO |
| Deliver only matching events | SNS Message Filtering |
| Long-term storage and retry | SQS |
| Broadcast notifications | SNS |
| Analytics pipeline | SNS → Kinesis Data Firehose → S3 |

## 🎯 Memory Trick

Think of **SNS as a TV broadcasting station** and **SQS as DVR recorders**.

- **SNS** broadcasts the program to everyone at the same time.
- **Each SQS queue** records its own copy.
- Every department (Shipping, Fraud, Analytics) watches **its own recording whenever it's ready**.
- **Filter policies** are like TV channel subscriptions—you only receive the channels (messages) you care about.
- **FIFO** means the episodes always arrive in the correct order, with no duplicate episodes.
