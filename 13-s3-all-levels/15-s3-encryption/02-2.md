# Amazon S3 Encryption — Final Exam Notes (SAA-C03)

There are actually **5 encryption/security concepts** that students often mix up:

1. **SSE-S3**
2. **SSE-KMS**
3. **SSE-C**
4. **Client-Side Encryption**
5. **Encryption in Transit (SSL/TLS)** ← This is NOT object encryption.

Let's understand them one by one.

---

# First Understand Two Different Things

Many students confuse these.

## 1. Encryption At Rest

Means:

> Data is encrypted **while stored** in S3.
> 

Example:

```
Laptop
   │
Upload
   ▼
Amazon S3
   │
Encrypt
   ▼
Stored Encrypted
```

This includes:

- ✅ SSE-S3
- ✅ SSE-KMS
- ✅ SSE-C
- ✅ Client-side Encryption

---

## 2. Encryption In Transit

Means:

> Data is encrypted **while travelling through the network**.
> 

Example

```
Laptop
      │
 Internet
      │
Amazon S3
```

If someone intercepts the network traffic,

they should NOT be able to read it.

This is achieved using:

> HTTPS (SSL/TLS)
> 

Notice:

Encryption in transit has NOTHING to do with how data is stored inside S3.

---

# Example

Suppose you upload

```
salary.xlsx
```

There are TWO stages.

## Stage 1

Laptop → S3

Need

```
HTTPS
```

to protect the network.

---

## Stage 2

Inside S3

Need

```
SSE-S3

or

SSE-KMS

or

SSE-C
```

to protect stored data.

---

```
 HTTPS

      ▼
Stored Encrypted
```

# Now Understand All Five

---

# 1. SSE-S3

Who encrypts?

AWS S3.

Who owns keys?

AWS.

Who manages keys?

AWS.

Flow

```
Upload

↓

S3

↓

Encrypt

↓

Store
```

Very simple.

Good for most applications.

---

# 2. SSE-KMS

Who encrypts?

AWS S3.

Where is the key?

AWS KMS.

Flow

```
Upload

↓

S3

↓

Ask KMS

↓

Encrypt

↓

Store
```

Notice:

Encryption still happens inside S3.

Only the key comes from KMS.

---

# What Happens During Upload?

Suppose:

```
report.pdf
```

Upload starts.

Step 1

```
S3

↓

Calls KMS

↓

GenerateDataKey API
```

KMS creates a temporary data encryption key.

---

Step 2

```
S3

↓

Uses Data Key

↓

Encrypts report.pdf
```

---

Step 3

Encrypted object stored.

---

# Download Process

Suppose:

```
Download report.pdf
```

S3 cannot decrypt alone.

First:

```
S3

↓

Calls

Decrypt API

↓

KMS
```

KMS returns the decrypted data key.

Then:

```
S3

↓

Decrypt Object

↓

Return File
```

---

# Why Does AWS Mention KMS Limits?

Because EVERY upload/download talks to KMS.

Imagine:

100,000 uploads per second.

Every upload does

```
GenerateDataKey
```

Every download does

```
Decrypt
```

Those APIs have quotas.

Example

Region quota:

```
5500 requests/sec
```

Suppose

```
7000 uploads/sec
```

Result:

```
5500

Allowed

1500

Throttled
```

This is called

## KMS Throttling

---

# Solution

AWS lets you increase quotas using:

**Service Quotas**

or redesign your application if needed.

Answer:

KMS API quota.

NOT

# Comparison of All Five

| Feature | SSE-S3 | SSE-KMS | SSE-C | Client-Side | HTTPS (SSL/TLS) |
| --- | --- | --- | --- | --- | --- |
| Purpose | Encrypt stored data | Encrypt stored data | Encrypt stored data | Encrypt before upload | Encrypt network traffic |
| Encryption Location | S3 | S3 | S3 | Client | Network |
| Who Manages Keys | AWS S3 | AWS KMS | Customer | Customer | SSL/TLS certificates |
| AWS Stores Keys | ✅ Yes | ✅ Yes (KMS) | ❌ No | ❌ No | N/A |
| Customer Controls Keys | ❌ | ✅ (especially with customer-managed KMS keys) | ✅ | ✅ | N/A |
| CloudTrail Audit | ❌ | ✅ | ❌ | ❌ | N/A |
| KMS API Calls | ❌ | ✅ | ❌ | ❌ | ❌ |
| Extra Cost | ❌ | ✅ | ❌ | ❌ | ❌ |
| Lose Key = Lose Data | ❌ | Usually no (if KMS key still exists and permissions remain) | ✅ | ✅ | N/A |
| HTTPS Required | Recommended | Recommended | ✅ Mandatory | Recommended | It's the feature itself |

# Which One Should You Choose?

| Requirement | Best Choice |
| --- | --- |
| Simple encryption | SSE-S3 |
| Audit logs and IAM control | SSE-KMS |
| AWS must never store your key | SSE-C |
| Encrypt before data leaves your computer | Client-Side Encryption |
| Protect data while traveling over the internet | HTTPS (SSL/TLS) |

# Easy Memory Trick

Imagine sending a **locked box** through a courier.

### 🟢 SSE-S3

The warehouse locks the box using **its own lock**.

---

### 🔵 SSE-KMS

The warehouse locks the box, but gets the lock from a **high-security key vault (KMS)** that records every use.

---

### 🟠 SSE-C

You bring your **own lock** to the warehouse. They use it but never keep a copy of the key.

---

### 🔴 Client-Side Encryption

You lock the box **at home** before giving it to the courier. The warehouse never sees what's inside.

---

### 🟣 HTTPS (Encryption in Transit)

The **truck transporting the box** is armored and secure. This protects the box **while it's being transported**, not how it's stored afterward.

---

# 🎯 30-Second SAA-C03 Summary

- **SSE-S3**: AWS S3 manages and stores the encryption keys. Simple, default, and uses AES-256.
- **SSE-KMS**: S3 encrypts the object using keys from AWS KMS. Every upload calls **GenerateDataKey**, and every download calls **Decrypt**, so high request rates can hit **KMS API quotas**. It provides auditing, IAM integration, and key management.
- **SSE-C**: You provide the encryption key with every request. AWS never stores it. HTTPS is mandatory because the key is transmitted with the request.
- **Client-Side Encryption**: You encrypt before uploading. AWS only stores encrypted data and never sees the plaintext.
- **Encryption in Transit (HTTPS/SSL/TLS)**: Protects data while moving between the client and S3. It is separate from object encryption at rest. Bucket policies using `aws:SecureTransport` can deny all non-HTTPS requests.
