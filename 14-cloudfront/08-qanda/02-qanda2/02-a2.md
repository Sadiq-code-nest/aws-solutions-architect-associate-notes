# AWS SAA-C03 Post-Mortem — CloudFront Private Content: Signed Cookies vs Signed URLs

## 1. Restate the Scenario in Plain English

The company already has a web application using **Amazon CloudFront** in front of an **Amazon S3 bucket**.

CloudFront distributes:

- Images
- Videos
- Static files

to users globally.

Now the company introduces **member-only premium media**. Only users who have paid should be able to access those private files.

The important requirement is:

> **Multiple private files must be accessible to subscribers without changing the existing URLs.**
> 

That last part is the biggest clue.

### Actors

| Actor | Role |
| --- | --- |
| Users/viewers | Request images/videos |
| Paying subscribers | Should access private media |
| Non-members | Must be denied |
| CloudFront | Distributes the media globally |
| S3 | Stores the actual media |
| Application | Determines whether the user is entitled to premium content |

### Current architecture

```
                    Users
               🌎 🌍 🌏
                    │
                    │ Existing URLs
                    ▼
             ┌──────────────┐
             │  CloudFront  │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │      S3      │
             │ Media Bucket │
             └──────────────┘
```

### Desired architecture

```
                    User
                     │
              Existing URL
                     │
                     ▼
              ┌─────────────┐
              │ CloudFront  │
              └──────┬──────┘
                     │
             Signed Cookie
                     │
             ┌───────┴───────┐
             │               │
          Member          Non-member
             │               │
             ▼               ▼
        Premium media      DENIED
```

The URL stays the same.

That points strongly toward **CloudFront Signed Cookies**.

# 2. Identify the Hidden Sub-Problems

There are actually several requirements hidden in the question.

| Symptom | Underlying Category | Why |
| --- | --- | --- |
| Only paying subscribers should access media | CloudFront private-content access control | Need authorization before serving private content |
| Multiple private media files | Access to multiple resources | Need a mechanism that can authorize a group of files |
| Current URLs must not change | URL-preserving authorization | Signed URLs modify the URL by adding query-string parameters |
| Existing CloudFront distribution should remain | CloudFront private-content mechanism | CloudFront supports signed URLs and signed cookies |
| Application knows whether user is a member | Application-level authorization | Application can issue authorization credentials to valid subscribers |

### The key distinction

```
ONE private file
     │
     ▼
Signed URL
```

versus:

```
MANY private files
     │
     ▼
Signed Cookie
```

And the question adds:

```
"without changing current URLs"
             │
             ▼
       Signed Cookie
```

# 3. Explain Every Option in Plain Language

## Option 1 — Match Viewer

> Configure your CloudFront distribution to use Match Viewer as its Origin Protocol Policy.
> 

### What is this trying to say?

It is saying:

> "Let CloudFront communicate with S3 using the same HTTP/HTTPS protocol that the viewer used."
> 

```
User
 │
 │ HTTP or HTTPS
 ▼
CloudFront
 │
 │ Match Viewer
 │
 ├── HTTP ──► S3
 └── HTTPS ─► S3
```

### Verdict: ❌ Incorrect

**Match Viewer has nothing to do with determining whether a user is a paying subscriber.**

It controls the **protocol used between CloudFront and the origin** based on the viewer request.

It does not perform:

```
Is user a member?
       │
   ┌───┴───┐
  YES      NO
   │        │
 Allow     Deny
```

So this option solves a completely different problem.

### Mini-topic: Origin Protocol Policy

CloudFront's origin protocol policy controls how CloudFront connects to the origin.

Common concepts include:

- HTTP only
- HTTPS only
- Match Viewer

Think:

> **Origin Protocol Policy = How CloudFront talks to origin.**
> 

Not:

> **Who is allowed to access the content.**
> 

---

# Option 2 — Signed Cookies

> Use Signed Cookies to control who can access private files by modifying the application to determine whether a user should have access. For members, send the required `Set-Cookie` headers to the viewer.
> 

### What is this saying?

The application authenticates the user.

If the user is a paying subscriber, the application gives them CloudFront authorization information in cookies.

Then the user can request multiple private files using the **same existing URLs**.

```
                     User
                       │
                 Login / Request
                       │
                       ▼
                Application
                       │
                Is subscriber?
                  /          \
                YES           NO
                 │             │
          Set-Cookie          DENY
                 │
                 ▼
             Browser
                 │
        ┌────────┼─────────┐
        │        │         │
      image    video     media
        │        │         │
        ▼        ▼         ▼
                CloudFront
                    │
                    ▼
                    S3
```

### Verdict: ✅ Correct

This perfectly satisfies the requirements.

The user can access:

```
https://example.com/images/a.jpg
https://example.com/images/b.jpg
https://example.com/videos/movie.mp4
```

without modifying those URLs.

The authorization is carried through the cookie.

### Why this is the best answer

The question contains two very important clues:

> **"multiple private media files"**
> 

and

> **"without having to change the current URLs."**
> 

That's almost a direct description of **CloudFront Signed Cookies**.

---

# Option 3 — Signed URL with Custom Policy

> Create a Signed URL with a custom policy which only allows members to see the private files.
> 

### What is this trying to say?

Create a special URL containing authorization information.

For example:

```
https://example.com/movie.mp4
    ↓
https://example.com/movie.mp4
   ?Expires=...
   &Signature=...
   &Key-Pair-Id=...
```

CloudFront validates the signature before allowing access.

```
User
 │
 ▼
Signed URL
 │
 ▼
CloudFront
 │
 ├── Valid → S3
 │
 └── Invalid → DENY
```

### Verdict: ❌ Incorrect for this requirement

Signed URLs are absolutely capable of protecting private CloudFront content.

The problem is the requirement:

> **"without having to change the current URLs."**
> 

A signed URL requires authorization information to be included in the URL.

Therefore, for many private objects:

```
file1 → signed URL
file2 → signed URL
file3 → signed URL
file4 → signed URL
```

A signed cookie is cleaner:

```
Cookie
  │
  ├── file1
  ├── file2
  ├── file3
  └── file4
```

### Mini-topic: Custom Policy

A CloudFront signed URL/cookie can use a policy to define conditions such as:

- expiration
- allowed resource
- IP restrictions

A **custom policy** gives more flexibility than a canned policy.

But:

> Custom policy doesn't make a signed URL stop being a URL-based authorization mechanism.
> 

---

# Option 4 — Field-Level Encryption

> Configure CloudFront to use Field-Level Encryption to protect private data and only allow access to members.
> 

### What is this trying to say?

Encrypt sensitive fields in an HTTP request before they reach the origin.

```
User
 │
 ▼
CloudFront
 │
 │ Encrypt sensitive field
 ▼
Origin
```

### Verdict: ❌ Incorrect

Field-Level Encryption is about **protecting sensitive data fields**, particularly data submitted by users.

For example:

```
POST /payment

{
   "name": "John",
   "cardNumber": "...."
}
```

Field-Level Encryption can protect selected fields.

It is **not a mechanism for saying:**

```
Paying subscriber → allow premium video
Non-subscriber → deny premium video
```

So this option solves a different security problem.

# 4. Deep-Dive Every AWS Concept Touched by the Question

## 4.1 Amazon CloudFront

### Definition

Amazon CloudFront is AWS's global content delivery network. It caches and delivers content from origins such as S3, ALB, or custom HTTP servers through globally distributed edge locations.

```
                 Global Users
             /       |       \
            ▼        ▼        ▼
         Edge-A    Edge-B   Edge-C
            \        |       /
             \       |      /
              └── CloudFront
                     │
                     ▼
                    S3
```

### Worked example

A user in Bangladesh requests:

```
/images/logo.png
```

CloudFront can serve it from a nearby edge location rather than requiring every request to travel directly to the S3 origin.

### CloudFront vs S3

| CloudFront | S3 |
| --- | --- |
| Content delivery layer | Object storage |
| Global edge locations | Regional storage |
| Caching | Stores objects |
| Can enforce signed URL/cookie access | Can use bucket/IAM policies |
| Can integrate with WAF | Provides object storage |

### Exam trigger

> **"Global users + static content + low latency" → CloudFront.**
> 

---

# 4.2 CloudFront Signed URL

### Definition

A signed URL is a CloudFront URL containing a cryptographic signature that authorizes access to a protected resource for a specified period/condition.

Conceptually:

```
Normal URL:
https://example.com/video.mp4

Signed URL:
https://example.com/video.mp4
             + authorization parameters
```

### Worked example

A user purchases a movie.

The application generates a signed URL valid for 1 hour:

```
User
 │
 ▼
Signed URL
 │
 ▼
CloudFront
 │
 ├── Valid signature → Serve
 └── Invalid/expired → Deny
```

### Signed URL vs Signed Cookie

| Signed URL | Signed Cookie |
| --- | --- |
| Authorization is in URL | Authorization is in cookies |
| Good for individual files | Good for multiple files |
| URL changes | Existing URL can remain unchanged |
| Easy to share as a specific link | Better for sessions accessing many resources |
| Query parameters contain signature/policy | Browser automatically sends cookie |

### Exam trigger

> **"Restrict access to individual files / downloadable file / one object" → Signed URL.**
> 

---

# 4.3 CloudFront Signed Cookie

### Definition

Signed cookies allow CloudFront to authorize access to private content without putting the authorization information into each URL. The browser sends the cookies automatically with requests.

```
Application
    │
    │ Set-Cookie
    ▼
 Browser
    │
    ├── /image1.jpg
    ├── /image2.jpg
    ├── /video1.mp4
    └── /video2.mp4
            │
            ▼
       CloudFront
            │
       Validate cookie
            │
            ▼
           S3
```

### Worked example

A subscriber logs in.

Application:

```
Subscriber = YES
       │
       ▼
Set CloudFront signed cookies
```

Now the user can access:

```
/images/premium1.jpg
/images/premium2.jpg
/videos/premium1.mp4
/videos/premium2.mp4
```

using their existing URLs.

### Signed Cookie vs Signed URL

| Signed Cookie | Signed URL |
| --- | --- |
| Best for multiple restricted resources | Best for individual restricted resources |
| Doesn't modify URLs | Adds signature parameters to URL |
| Good for subscriber/member access | Good for controlled downloads |
| Browser automatically sends cookie | User must use signed URL |

### Exam trigger

> **"Multiple private files + existing URLs must remain unchanged" → CloudFront Signed Cookies.**
> 

---

# 4.4 CloudFront Origin Protocol Policy

### Definition

The origin protocol policy determines how CloudFront communicates with its origin.

```
Viewer
  │
  │ HTTPS
  ▼
CloudFront
  │
  │ Origin Protocol Policy
  ▼
Origin/S3
```

This is about **transport protocol**, not user authorization.

### Worked example

Suppose:

```
Viewer → HTTPS → CloudFront
```

With appropriate origin protocol configuration, CloudFront can communicate with the origin using HTTPS.

### Origin Protocol Policy vs Viewer Protocol Policy

| Origin Protocol Policy | Viewer Protocol Policy |
| --- | --- |
| CloudFront → Origin | Viewer → CloudFront |
| Controls origin connection | Controls viewer connection |
| HTTP/HTTPS behavior | HTTP/HTTPS behavior |
| Doesn't determine authorization | Doesn't determine membership |

### Exam trigger

> **"How CloudFront connects to origin" → Origin Protocol Policy.**
> 

---

# 4.5 CloudFront Field-Level Encryption

### Definition

CloudFront Field-Level Encryption encrypts sensitive fields in POST/PUT requests before forwarding them to the origin. It is intended to protect specific pieces of submitted data rather than control who can access an object.

```
User
 │
 │ POST request
 ▼
CloudFront
 │
 │ Encrypt selected fields
 ▼
Origin
```

### Worked example

A checkout application sends:

```
{
  "name": "Alice",
  "cardNumber": "..."
}
```

Only `cardNumber` may be encrypted.

### Field-Level Encryption vs CloudFront Signed Cookies

| Field-Level Encryption | Signed Cookie |
| --- | --- |
| Protects sensitive request fields | Controls access to private content |
| Encrypts selected data | Authorizes viewer |
| Primarily request → origin | Viewer → CloudFront authorization |
| Not an access-control mechanism | Access-control mechanism |

### Exam trigger

> **"Encrypt specific sensitive fields before sending to origin" → Field-Level Encryption.**
> 

---

# 4.6 S3 Origin

### Definition

Amazon S3 can act as an origin for CloudFront. S3 stores the actual media objects while CloudFront provides global distribution and caching.

```
User
 │
 ▼
CloudFront
 │
 │ Cache miss
 ▼
S3
 │
 ▼
Object
 │
 ▼
CloudFront
 │
 ▼
User
```

### Worked example

```
S3:
premium/movie.mp4
```

CloudFront distributes it globally.

### S3 vs CloudFront

| S3 | CloudFront |
| --- | --- |
| Stores object | Delivers object |
| Origin | Distribution layer |
| Regional | Global edge network |
| Storage | Caching/CDN |

### Exam trigger

> **"Static files stored in S3 and globally delivered" → S3 + CloudFront.**
>

# 8. Why the Tempting Wrong Answers Are Tempting

## 🪤 Option 3 — Signed URL

This is the strongest distractor.

Why does it sound correct?

Because **Signed URLs absolutely are used for CloudFront private content**.

A rushed reader sees:

> "private media + CloudFront"
> 

and immediately chooses:

> Signed URL.
> 

But the question gives an additional requirement:

> **Multiple files + existing URLs cannot change.**
> 

That's what separates the two:

```
                    Private Content
                          │
                 ┌────────┴────────┐
                 │                 │
             One/few files     Many files
                 │                 │
                 ▼                 ▼
           Signed URL       Signed Cookie
                 │                 │
          URL changes       URL unchanged
```

---

## 🪤 Option 1 — Match Viewer

The trap here is seeing words related to **HTTP/HTTPS** and thinking:

> "HTTPS = secure = correct."
> 

But **HTTPS transport security and authorization are different things**.

```
HTTPS
 │
 ▼
Protects data in transit

Signed Cookie
 │
 ▼
Controls who gets private content
```

The requirement is **authorization**, not simply HTTPS.

## ✅ Correct Answer

**Option 2 — Use CloudFront Signed Cookies.**

The application determines whether the user is a paying member and, for authorized users, sends the required signed cookies. The user can then access multiple private media files using the **existing URLs**.

If the application can generate a signed URL for each object:

**Signed URLs can work.**

---

If the question says:

> "Encrypt credit-card fields in POST requests before they reach the origin."
>

**CloudFront Field-Level Encryption.**

Not Signed Cookies.

---

### Trap 4 — Force HTTPS

If the question says:

> "Ensure users always access CloudFront using HTTPS."
> 

Think:

**CloudFront Viewer Protocol Policy → Redirect HTTP to HTTPS / HTTPS only.**

That's different from private-content authorization.

---

### Trap 5 — Secure CloudFront's connection to S3

If the question says:

> "Ensure CloudFront connects securely to the origin."
> 

Think:

**Origin Protocol Policy / HTTPS**, depending on the origin and exact requirement.
