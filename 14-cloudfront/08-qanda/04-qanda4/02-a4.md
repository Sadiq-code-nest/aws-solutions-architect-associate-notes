# A4

## 1. ✅ Correct Answer

### **Option 1 — Create an Origin Access Control (OAC) and give it permission to read the S3 objects.**

### **Option 5 — Require users to access the private content using CloudFront signed URLs or signed cookies.**

These two solve **two different security layers**:

```
                 USER / CLIENT
                      │
              Signed URL/Cookie
                      │
                      ↓
              ┌───────────────┐
              │  CloudFront   │
              └───────────────┘
                      │
                     OAC
                      │
                      ↓
                 Private S3
```

- **CloudFront Signed URL/Cookie** → controls **which client/user is allowed to access the content through CloudFront**.
- **OAC** → controls **whether S3 can be accessed through CloudFront and prevents direct S3 access**.

### The critical exam logic

The question has **two separate requirements**:

1. **Only a specific client should access the private content** → **Signed URL / Signed Cookie**
2. **Content must be served through CloudFront only, not directly from S3** → **OAC + S3 bucket policy**

That's why the answer is **OAC + CloudFront signed URLs/cookies**.

# 2. 🧠 Core Concept — Very Simple

### Translation:

> **"Make S3 private so clients cannot bypass CloudFront, and then make CloudFront give the private files only to authorized clients."**
> 

There are actually **two gates**:

```
Gate 1: Can you reach S3 directly?
                ↓
          OAC protects S3
                ↓
          NO direct S3 access

Gate 2: Can you access private content through CloudFront?
                ↓
       Signed URL / Cookie
                ↓
          Authorized client
```

### Think of it like a private building:

**OAC = locks the back door**

> Nobody can walk directly into the S3 bucket.
> 

**Signed URL/Cookie = gives a specific person a temporary access pass**

> Only authorized clients can get the private content through CloudFront.
> 

---

# 3. ✅ Why the Correct Answers Are Correct

## Option 1 — Origin Access Control (OAC) ✅

The requirement says:

> **"serve the private content via CloudFront only"**
> 

Currently:

```
Client
 ├────────→ S3 URL ❌
 │
 └────────→ CloudFront → S3
```

The problem is that clients can **bypass CloudFront**.

With OAC:

```
Client
 │
 └────────→ CloudFront
                 │
                 ↓
                OAC
                 │
                 ↓
              Private S3
```

You configure the S3 bucket policy to allow the CloudFront distribution/OAC to access the objects.

Then:

```
Direct S3 URL
     ↓
   DENIED ❌
```

while:

```
CloudFront
     ↓
    OAC
     ↓
     S3
     ↓
   ALLOWED ✅
```

### Requirement checklist

| Requirement | OAC |
| --- | --- |
| Keep S3 objects private | ✅ |
| Prevent direct S3 access | ✅ |
| Allow CloudFront to access S3 | ✅ |
| Serve content through CloudFront | ✅ |
| Replace public S3 access | ✅ |
| Identify a specific client | ❌ |
| Restrict access to authorized CloudFront users | ❌ |

That last point is why **OAC alone isn't enough**.

---

## Option 5 — CloudFront Signed URLs / Signed Cookies ✅

Now we need to solve:

> **"Only that specific client can access the content."**
> 

CloudFront provides **signed URLs** and **signed cookies** for restricting access to private content.

Example:

```
Normal URL:
https://example.cloudfront.net/movie.mp4

Private URL:
https://example.cloudfront.net/movie.mp4
      + signed parameters
```

CloudFront validates the signature before allowing access.

```
Client
  │
  │ Signed URL
  ↓
CloudFront
  │
  ├── Signature valid? → YES → S3
  │
  └── Signature valid? → NO → ❌ Access denied
```

### Signed URL vs Signed Cookie

**Signed URL**

Good when granting access to a **specific object**.

```
client → signed URL → specific-file.pdf
```

**Signed Cookie**

Useful when the client needs access to **multiple private files**.

```
client
  ↓
signed cookie
  ↓
CloudFront
  ↓
multiple private files
```

This is particularly useful for your question because the scenario talks about **private content/files**.

# 4. ❌ Why Every Other Option Is Wrong

## Option 2 — CloudFront Origin Shield ❌

Origin Shield is **not an authorization mechanism**.

Its purpose is primarily to improve caching efficiency and reduce load on the origin by providing an additional centralized caching layer.

Think:

```
Users
 ↓
CloudFront Edge
 ↓
Origin Shield
 ↓
Origin
```

It can help with:

- origin load reduction
- cache efficiency
- consolidating requests from multiple edge locations

But it does **not** mean:

```
Origin Shield → "Only Client A is authorized"
```

❌ It doesn't provide client-level private-content authorization.

### Exam distinction

> **Origin Shield = origin protection/caching efficiency**
> 

> **OAC = CloudFront-to-S3 authorization**
> 

> **Signed URL/Cookie = viewer authorization**
> 

---

## Option 3 — CloudFront Function to check clients ❌

This sounds tempting because the requirement says:

> **"only that client can access the data."**
> 

You might think:

```
CloudFront Function
       ↓
Check client
       ↓
Allow / Deny
```

But that's not the intended standard mechanism for **CloudFront private content access**.

CloudFront provides **signed URLs and signed cookies specifically for controlling access to private content**.

Using a custom function to implement your own authorization logic adds unnecessary complexity.

### Exam principle

If AWS already provides a purpose-built feature:

```
Private CloudFront content
       ↓
Signed URL / Signed Cookie
```

don't unnecessarily build custom authorization logic.

---

## Option 4 — S3 Presigned URL ❌

This is an important trap.

An **S3 presigned URL** gives temporary access **directly to an S3 object**.

For example:

```
Client
  │
  └────→ S3 presigned URL
                ↓
              S3
```

But the requirement is:

> **"serve the private content via CloudFront only"**
> 

That means we don't want:

```
Client → S3
```

We want:

```
Client → CloudFront → S3
```

Therefore, an S3 presigned URL is the wrong authorization mechanism for this architecture.

### Don't confuse:

| Mechanism | Controls |
| --- | --- |
| **S3 presigned URL** | Temporary direct access to S3 |
| **CloudFront signed URL** | Temporary access through CloudFront |
| **CloudFront signed cookie** | Access to multiple private CloudFront objects |

### ⭐ Exam trap

If the question says:

> **"private content through CloudFront"**
> 

Think:

**CloudFront Signed URL/Cookie**

NOT:

**S3 presigned URL**

# 7. 🏢 Easy Real-World Example

Imagine a company selling premium training videos.

Their files are stored in:

```
S3
├── free-video.mp4
├── premium-video-1.mp4
├── premium-video-2.mp4
└── premium-video-3.mp4
```

The company wants only paying customers to access premium videos.

### ❌ Bad architecture

```
Customer
 ├──────────────→ S3 URL
 │
 └──────────────→ CloudFront
```

Customers can bypass CloudFront.

---

### ✅ Correct architecture

First, make S3 private:

```
Customer
    ↓
CloudFront
    ↓
OAC
    ↓
Private S3
```

Then authorize the customer:

```
Customer
    ↓
Signed Cookie
    ↓
CloudFront
    ↓
OAC
    ↓
S3
```

Now:

```
Direct S3 URL → ❌ DENIED

CloudFront without authorization → ❌ DENIED

CloudFront + valid signed URL/cookie → ✅ ALLOWED
```

That's exactly the security model this question is testing.

# 10. 📝 SAA-C03 Exam Takeaway

**For private S3 content delivered only through CloudFront, use OAC to block direct S3 access and CloudFront signed URLs/cookies to authorize specific viewers.**
