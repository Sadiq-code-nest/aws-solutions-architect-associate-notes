# KMS Key Types

There are **two main cryptographic key types**.

```
KMS Keys

│

├── Symmetric

└── Asymmetric
```

---

# 1. Symmetric Key ⭐⭐⭐⭐⭐

This is by far the most common.

One single key is used for:

- Encrypt
- Decrypt

Think:

```
Same Key

↓

Lock

↓

Unlock
```

---

## Example

House key.

Same key:

Locks the door.

Unlocks the door.

Exactly how symmetric encryption works.

---

# AWS Services Use Symmetric Keys

Examples:

- S3
- EBS
- RDS
- DynamoDB
- EFS

Nearly every AWS service integrated with KMS uses s**ymmetric (AES-256)** keys.

---

# Diagram

```
Encrypt

↓

AES Key

↓

Decrypt
```

One key does both jobs.

---

# Important Exam Tip

You never download the symmetric KMS key.

Instead:

Applications call:

```
KMS API

↓

Encrypt

or

Decrypt
```

The key never leaves KMS in plaintext.

---

# 2. Asymmetric Key

Uses two keys.

```
Public Key

Private Key
```

---

# Public Key

Anyone can download it.

Anyone can encrypt data.

---

# Private Key

Stored securely inside KMS.

Never downloadable in plaintext.

Only KMS uses it.

---

# Example

Imagine a mailbox.

Anyone can put letters inside.

(Public Key)

Only the owner has the mailbox key.

(Private Key)

---

# Diagram

```
Public Key

↓

Encrypt

↓

Encrypted Message

↓

Private Key

↓

Decrypt
```

---

# Real-Life Example ⭐⭐⭐⭐⭐

A customer wants to encrypt data from their laptop before sending it to AWS, but the laptop cannot call the KMS API.

The customer downloads the **public key**, encrypts the data locally, and AWS/KMS later decrypts it with the **private key**.

---

# KMS Key Ownership Types

This topic appears frequently in the exam.

There are **4 kinds of KMS keys**.

---

# 1. AWS Owned Keys ⭐⭐⭐⭐⭐

These are completely managed by AWS.

You don't see them.

You don't manage them.

Examples:

- Default encryption for DynamoDB
- SSE-S3
- SSE-SQS

Think:

AWS owns everything.

---

# Example

You enable default encryption on DynamoDB.

AWS automatically uses an AWS-owned key.

You never interact with it.

---

# 2. AWS Managed Keys

Key name looks like:

```
aws/s3

aws/ebs

aws/rds
```

AWS creates them inside **your account** and manages them for you.

Automatic rotation happens every year.

---

# Example

You enable RDS encryption.

AWS uses:

```
aws/rds
```

Very simple.

---

# 3. Customer-Managed Keys (CMK) ⭐⭐⭐⭐⭐

You create the key.

You control:

- Permissions
- Rotation
- Policies
- Enable/Disable
- Delete

This gives you the most flexibility.

---

## Example

A bank wants only its security team to use a specific encryption key.

They create a c**ustomer-managed key** and define exactly who can use it.

---

# 4. Imported Keys

You already have an encryption key from another system (for example, an on-premises HSM) and import it into KMS.

You are responsible for managing and rotating that key material.

---

# Key Rotation

Keys should not be used forever.

Imagine your house key.

After 20 years,

Someone may have copied it.

So you change the lock.

Same with KMS.

---

# AWS Managed Key

Automatically rotates every year.

Nothing to configure.

---

# Customer Managed Key

Automatic rotation can be enabled, or you can rotate it on demand.

---

# Imported Key

No automatic rotation.

You must manually import new key material (often by changing the alias to point to a new key).

---

# Snapshot Copy Across Regions

Suppose:

London Region:

```
EBS Volume

↓

Encrypted

↓

Key A
```

Now copy to Singapore.

Can Singapore use Key A?

No.

KMS keys are **Regional**.

You must re-encrypt using a KMS key in the destination Region.

---

# Diagram

```
London

EBS

↓

Key A

↓

Snapshot

↓

Copy

↓

Singapore

↓

KMS Re-Encrypt

↓

Key B

↓

New Snapshot
```

Remember:

**Different Region → Different KMS Key**

---

# KMS Key Policies

Very important.

KMS uses **Key Policies** to control who can use a KMS key.

Think of them like **S3 Bucket Policies**, but specifically for KMS keys.

Without a suitable key policy, access is denied—even if an IAM policy allows it.

---

# Example

Company creates:

```
Finance Key
```

Key Policy:

```
Allow

Finance Role

Decrypt
```

Developer Role:

```
Denied
```

Only Finance can use that key.

---

# Default Key Policy

If you create a key and don't specify a custom policy:

AWS creates a default policy that gives the account's root principal full control over the key.

---

# Custom Key Policy

You can define:

- Who can encrypt
- Who can decrypt
- Who can administer the key
- Cross-account access

---

# Cross-Account Snapshot Sharing

Imagine:

Account A

↓

Encrypted Snapshot

↓

Customer-Managed Key

Now share it with:

Account B

The snapshot cannot be used unless:

1. The **KMS Key Policy** allows Account B to use the key.
2. Account B copies the snapshot and re-encrypts it with a KMS key in **its own account**.

---

# Architecture

```
Account A

Snapshot

↓

Encrypted

↓

Customer Managed Key

↓

Share Snapshot

↓

Account B

↓

Allowed by Key Policy

↓

Copy Snapshot

↓

Encrypt with Account B Key

↓

Create Volume
```

# KMS vs Secrets Manager

Many students confuse these.

| AWS KMS | AWS Secrets Manager |
| --- | --- |
| Stores encryption keys | Stores secrets (passwords, API keys, tokens) |
| Encrypts/decrypts data | Uses KMS to encrypt secrets |
| Key management | Secret management |

Think:

- **KMS = Key Vault**
- **Secrets Manager = Password Vault**

---

# KMS vs CloudHSM

| KMS | CloudHSM |
| --- | --- |
| AWS manages the hardware | You manage the HSM |
| Easier to use | More control |
| Integrated with many AWS services | Used for specialised compliance needs |

# AWS SAA-C03 Exam Tips

If the question says...

- **"Manage encryption keys for AWS services."**
    - ✅ **AWS KMS**
- **"Need full control over key permissions and rotation."**
    - ✅ **Customer Managed Key**
- **"`aws/s3` or `aws/rds` key."**
    - ✅ **AWS Managed Key**
- **"Need to encrypt data using one key for both encryption and decryption."**
    - ✅ **Symmetric Key**
- **"Need public/private key encryption."**
    - ✅ **Asymmetric Key**
- **"Copy an encrypted EBS snapshot to another Region."**
    - ✅ **Re-encrypt it with a KMS key in the destination Region**
- **"Share an encrypted snapshot with another AWS account."**
    - ✅ **Allow access through the KMS Key Policy, then copy and re-encrypt using a key in the target account**

## One-line Summary

**AWS KMS is AWS's managed encryption key service. It securely stores and controls encryption keys, integrates with IAM and CloudTrail, supports symmetric and asymmetric keys, and provides the encryption foundation for services like S3, EBS, RDS, DynamoDB, and many others.**
