# 18. Example — Banking application

Imagine an online banking application:

```
Customer
   │
   ▼
ALB
   │
   ▼
EC2 Auto Scaling
   │
   ▼
RDS MySQL
```

You don't want:

```
DB_PASSWORD=SuperSecretPassword
```

stored on the EC2 instances.

Instead:

### Step 1

Enable IAM DB Authentication:

```
RDS
└── IAM DB Authentication = Enabled
```

### Step 2

Create an EC2 IAM role:

```
BankingAppRole
```

### Step 3

Allow:

```
rds-db:connect
```

### Step 4

Configure the database user for IAM authentication.

### Step 5

Application obtains a temporary authentication token.

### Step 6

Application connects:

```
EC2
 ↓
Temporary Token
 ↓
RDS MySQL
```

No permanent database password is required for that IAM-authenticated connection.

# 20. What if the EC2 instance is replaced?

This is another reason IAM roles are useful.

Suppose:

```
EC2 #1
```

fails.

Auto Scaling launches:

```
EC2 #4
```

Because the IAM role is configured in the launch template:

```
EC2 #4
 ↓
Same IAM Role
 ↓
Can authenticate to RDS
```

You don't have to manually copy credentials to the new instance.

This is particularly useful for:

- Auto Scaling
- Dynamic workloads
- Ephemeral instances
- Containerized applications using appropriate IAM mechanisms

# 21. IAM DB Authentication and least privilege

You should not give the EC2 role unlimited access.

Bad:

```
AdministratorAccess
```

Better:

```
Allow only the required rds-db:connect
```

And restrict it to the required:

```
Database
+
Database user
```

This follows the **principle of least privilege**.

---

# 22. Does IAM DB Authentication provide database permissions?

Not directly.

Suppose:

```
IAM Role
```

can connect as:

```
appuser
```

That doesn't mean the application automatically gets:

```
DROP DATABASE
```

The database user's privileges determine what it can do.

For example:

```
IAM Role
   ↓
Can connect as appuser
   ↓
appuser
   ↓
SELECT
INSERT
UPDATE
```

The database controls the actual database privileges.

---

# 23. Does IAM DB Authentication encrypt data at rest?

❌ No.

IAM DB Authentication is not an encryption-at-rest feature.

For encryption at rest, use:

**RDS encryption with AWS KMS**

Think:

| Requirement | Solution |
| --- | --- |
| IAM-based authentication | IAM DB Authentication |
| Encryption in transit | SSL/TLS |
| Encryption at rest | KMS/RDS encryption |
| Network restriction | Security Groups |
| Store DB password | Secrets Manager |

---

# 24. Does IAM DB Authentication make RDS publicly accessible?

❌ No.

IAM DB Authentication has nothing to do with whether RDS is public/private.

You should still design the network properly.

Typical architecture:

```
Internet
   │
   ▼
ALB
   │
   ▼
EC2
   │
   ▼
Private RDS
```

RDS is normally placed in private subnets and protected with security groups.

   ▼

### IAM DB Authentication

# 28. Important limitation: connection overhead

IAM database authentication can introduce additional overhead compared with traditional password authentication because authentication tokens must be generated and connections authenticated.

For applications that make very large numbers of database connections, AWS recommends considering connection management carefully.

This is where **RDS Proxy** can become relevant.

Example:

```
Many EC2 instances
       │
       ▼
    RDS Proxy
       │
       ▼
      RDS
```

RDS Proxy can help manage database connections and improve application scalability/resilience.

For SAA, remember the distinction:

```
IAM DB Authentication
→ How the application authenticates

RDS Proxy
→ How database connections are managed
```

# 29. Connection pooling and IAM tokens

This is a more advanced but useful concept.

A temporary authentication token is used to establish/authenticate a database connection.

After a connection has been established, applications commonly maintain/reuse connections rather than obtaining a new token for every individual SQL query.

That's why connection pooling is important for production applications.

For SAA, you don't need to memorize implementation details, but understand:

> **IAM authentication is about authentication of database connections, not generating a new token for every SQL statement.**
>

# 31. The security model

You can remember RDS security as four layers:

```
                 RDS SECURITY
                      │
        ┌─────────────┼─────────────┐
        │             │             │
    Network      Authentication   Encryption
        │             │             │
 Security Group   IAM DB Auth     SSL/TLS
        │                         KMS
        │
 Private Subnet
```

More specifically:

### Network

**Security Group**

> Who can reach RDS?
> 

### Authentication

**IAM DB Authentication**

> Who can log in?
> 

### Encryption in transit

**SSL/TLS**

> Is traffic protected while traveling?
> 

### Encryption at rest

**KMS/RDS encryption**

> Is stored database data encrypted?
> 

This mental model is extremely useful for SAA.

# 32. Common exam traps

## Trap 1

> "Use SSL to authenticate EC2 to RDS."
> 

❌ SSL encrypts traffic; it isn't the answer for IAM-token authentication.

---

## Trap 2

> "Create an IAM role for EC2."
> 

⚠️ Necessary in an EC2-based IAM-authentication design, but not the complete RDS feature.

---

## Trap 3

> "Use STS to generate temporary credentials."
> 

❌ Don't confuse temporary AWS credentials with the RDS IAM authentication mechanism.

---

## Trap 4

> "Store the password in Secrets Manager."
> 

⚠️ Excellent for password management, but if the question explicitly says **IAM authentication token**, use IAM DB Authentication.

---

## Trap 5

> "Use Multi-AZ."
> 

❌ Multi-AZ is for availability, not authentication.

---

## Trap 6

> "Use Security Groups."
> 

❌ Security Groups control network access, not IAM database authentication.

# 36. IAM DB Authentication vs Security Group

Another must-know:

| Security mechanism | Job |
| --- | --- |
| Security Group | Network-level access |
| IAM DB Authentication | Database authentication |
| Database privileges | Database-level authorization |

```

 │
 │ Security Group
 │ "Can I reach port 3306?"
 ▼

 │
 │ IAM DB Authentication

```

That's a beautiful way to understand the entire security chain.

# 38. What you should memorize for the SAA exam

You don't need to memorize every implementation command.

Memorize these **10 points**:

### 1.

**IAM DB Authentication = IAM-based authentication for supported RDS databases.**

### 2.

It uses a **temporary authentication token**.

### 3.

It avoids the need for a **long-lived database password** for the IAM-authenticated connection.

### 4.

EC2 applications should use an **IAM role**, not hardcoded IAM access keys.

### 5.

The IAM role needs appropriate **`rds-db:connect`** permission.

### 6.

**IAM DB Authentication must be enabled on RDS.**

### 7.

The database still has a **database user** with database-level privileges.

### 8.

**Security Groups still control network connectivity.**

### 9.

**SSL/TLS is for encryption in transit**, not the same thing as IAM authentication.

### 10.

**Secrets Manager is for storing/rotating database secrets**, while IAM DB Authentication is for IAM-based database authentication.
