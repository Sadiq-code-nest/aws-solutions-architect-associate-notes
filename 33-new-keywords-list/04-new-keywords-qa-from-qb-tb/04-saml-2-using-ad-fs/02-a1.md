# A1

## 1. ✅ Correct Answer

**Set up SAML 2.0-Based Federation by using a Microsoft Active Directory Federation Service (AD FS).**

This is the best fit because the company already has **on-premises Active Directory credentials** and wants Software Architects to use those credentials to access **both on-premises and AWS resources**.

The key requirement is **enterprise identity federation from on-premises AD to AWS**.

```
On-Premises Active Directory
          │
          ↓
       AD FS
          │
      SAML 2.0
          │
          ↓
     AWS IAM / AWS
```

Users authenticate using their existing corporate credentials rather than maintaining separate IAM users.

---

# 2. 🧠 Core Concept — Very Simple

### What is the question REALLY asking?

> **"Our employees already have usernames/passwords in corporate Active Directory — how can they use those same identities to access AWS without creating separate AWS IAM users?"**
> 

Answer:

**AD + AD FS + SAML 2.0 Federation → AWS**

---

# 3. ✅ Why the Correct Answer Is Correct

### Requirement checklist

| Requirement | Does SAML 2.0 + AD FS satisfy it? |
| --- | --- |
| Users already exist in on-premises Active Directory | ✅ Yes |
| Use existing corporate credentials | ✅ Yes |
| Access AWS resources | ✅ Yes |
| Avoid creating individual IAM users | ✅ Yes |
| Integrate enterprise identity with AWS | ✅ Yes |
| Supports SSO/federated access | ✅ Yes |
| Uses standard federation protocol | ✅ SAML 2.0 |
| Works with Microsoft AD FS | ✅ Yes |

### Step-by-step

The company already has:

```
Corporate Network
      │
      ↓
Active Directory
      │
      ├── Architect A
      ├── Architect B
      └── Architect C
```

Instead of creating:

```
AWS IAM
 ├── IAM User A
 ├── IAM User B
 └── IAM User C
```

the company establishes federation.

```
User
 │
 │ Corporate credentials
 ↓
Active Directory
 │
 ↓
AD FS
 │
 │ SAML 2.0 assertion
 ↓
AWS
 │
 ↓
Temporary AWS credentials
 │
 ↓
AWS resources
```

### Why SAML 2.0?

**SAML (Security Assertion Markup Language) 2.0** is commonly used for **enterprise SSO/federation**.

The corporate identity provider authenticates the user and sends a SAML assertion to AWS. AWS then provides access based on the federated identity and associated IAM role.

So:

> **Corporate identity remains in AD; AWS trusts the identity provider.**
>

# 4. ❌ Why Every Other Option Is Wrong

## Option 1 — Use IAM users ❌

### What IAM Users do

An IAM user is an AWS identity with its own credentials and permissions.

```
AWS IAM
 ├── IAM User 1
 ├── IAM User 2
 └── IAM User 3
```

### Why it seems tempting

IAM users can absolutely access AWS resources.

But the question specifically says:

> **"using on-premises credentials, which are stored in Active Directory"**
> 

Creating IAM users would mean maintaining a **separate AWS identity system**.

### Why it fails

You would have:

```
AD credentials
       +
AWS IAM credentials
```

instead of:

```
AD credentials
       ↓
Federation
       ↓
AWS
```

The requirement is specifically **federated access using existing corporate credentials**.

---

## Option 2 — SAML 2.0 Federation using Microsoft AD FS ✅

**Correct.**

```
Active Directory
       ↓
     AD FS
       ↓
   SAML 2.0
       ↓
      AWS
```

This is the classic **on-premises Active Directory → AWS federation** scenario.

---

## Option 3 — SAML 2.0 Federation using Web Identity Federation ❌

This option intentionally mixes two different federation concepts.

### Web Identity Federation

Web identity federation is generally associated with users authenticated by **web identity providers**, such as social identity providers or other supported OIDC-based providers.

Conceptually:

```
User
 ↓
Web Identity Provider
 ↓
OIDC/Web Identity
 ↓
AWS
```

### Why it seems tempting

The option contains **"SAML 2.0 Federation"**, which sounds correct.

But the problem specifically involves:

> **Microsoft Active Directory + AD FS**
> 

For an enterprise Active Directory environment, **AD FS with SAML 2.0** is the appropriate federation approach.

### Important distinction

```
Corporate AD / AD FS
        ↓
    SAML 2.0
        ↓
       AWS

Web identity provider
        ↓
 OIDC/Web Identity
        ↓
       AWS
```

Don't confuse **SAML federation** with **Web Identity Federation**.

---

## Option 4 — Use Amazon VPC ❌

### What Amazon VPC does

Amazon VPC provides an isolated virtual network environment in AWS.

It handles networking concepts such as:

- Subnets
- Route tables
- Security groups
- Network connectivity
- Internet/NAT gateways

### Why it seems tempting

The question mentions resources in:

- On-premises network
- AWS cloud

That might make you think about networking.

### Why it fails

The actual problem is **identity authentication**, not network connectivity.

A VPC can establish network connectivity concepts, but it does not allow users to authenticate to AWS using their existing AD credentials.

```
VPC
 ↓
Networking

AD FS + SAML
 ↓
Identity / Authentication
```

# 7. 🏢 Easy Real-World Example

Imagine a pharmaceutical company has 5,000 employees.

Every employee already has a corporate account:

```
employee@company.com
        ↓
Active Directory
```

The company doesn't want employees to maintain another AWS username/password.

### Without federation

```
Employee
 ├── Corporate AD password
 └── AWS IAM credentials
```

Two identity systems → more administration.

### With federation

```
Employee
    │
    │ Corporate login
    ↓
Active Directory
    │
    ↓
AD FS
    │
    │ SAML 2.0
    ↓
AWS
    │
    ↓
Temporary AWS access
```

The employee can use the **existing corporate identity** to access AWS.

If the employee leaves the company and their AD account is disabled, their federated access can also be prevented.

# 9. 🔄 Similar Questions AWS Could Ask

### Variation 1

**A company has Microsoft Active Directory on premises and wants employees to access AWS using their existing corporate credentials.**

✅ **SAML 2.0 federation using AD FS**

### Variation 2

**A company wants employees to access multiple AWS accounts through a centralized corporate identity provider and SSO.**

✅ **Federation / IAM Identity Center with the corporate identity provider**, depending on the architecture described.

**Twist:** If the question specifically says **AD FS + SAML 2.0**, choose SAML federation.

---

### Variation 3

**A mobile application needs users to authenticate using social identity providers and obtain temporary AWS credentials.**

✅ **Amazon Cognito / web identity federation**

**Twist:** This is application/user identity rather than corporate AD federation.

---

### Variation 4

**A company needs private network connectivity between its on-premises data center and AWS resources.**

✅ **AWS Site-to-Site VPN or AWS Direct Connect**, depending on the requirements.

**Twist:** This is a **networking** problem, not an authentication problem.

---

### ⭐ Important distinction

| Requirement | Think of |
| --- | --- |
| Existing corporate AD credentials → AWS | **SAML 2.0 + AD FS** |
| AWS users with their own AWS identities | **IAM Users** |
| Temporary AWS permissions | **IAM Role** |
| App users / web identity | **Cognito / Web Identity Federation** |
| Private connectivity between on-premises & AWS | **VPN / Direct Connect** |
| AWS virtual network | **VPC** |

### 🔥 Exam trap

**SAML ≠ Web Identity Federation.**

If the question says:

> **Corporate Active Directory / AD FS**
> 

think:

**SAML 2.0 Federation**

If it says:

> **Web/mobile app + social/web identity provider**
> 

think:

**Web Identity / Cognito**
