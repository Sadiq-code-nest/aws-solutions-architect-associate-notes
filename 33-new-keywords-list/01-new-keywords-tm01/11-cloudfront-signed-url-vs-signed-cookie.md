# CloudFront Signed URL vs Signed Cookie

The easiest way to understand both is:

> **CloudFront Signed URL and Signed Cookie are ways to give authorized users temporary access to private content.**
> 

They are especially useful when you have:

```
User → CloudFront → Private S3 content
```

and you **don't want everyone on the internet to access that content**.

---

# 1. First understand the problem

Suppose you have a private video:

```
S3
└── premium-video.mp4
```

You don't want:

```
Anyone → premium-video.mp4 ❌
```

Only paying customers should access it.

You put CloudFront in front:

```
User
  │
  ▼
CloudFront
  │
  ▼
Private S3
```

Now CloudFront needs to determine:

> "Is this user allowed to access this private file?"
> 

That's where **Signed URL** and **Signed Cookie** come in.

---

# 2. What is a Signed URL?

A **Signed URL** is a normal CloudFront URL with additional security information attached to it.

For example, conceptually:

```
https://cdn.example.com/premium-video.mp4
    ?Expires=...
    &Signature=...
    &Key-Pair-Id=...
```

The signature proves that the URL was generated by an authorized signer.

---

# 3. How Signed URL works

Imagine your customer pays for a movie.

Your application verifies:

```
Customer
   ↓
Payment successful? ✅
```

Your backend then generates a signed CloudFront URL:

```
Backend
   │
   ▼
Signed URL
   │
   ▼
Customer
```

The customer gets:

```
https://cdn.example.com/movie.mp4?...signature...
```

They request it:

```
Customer
   │
   │ Signed URL
   ▼
CloudFront
   │
   ├── Signature valid? ✅
   ├── Not expired? ✅
   └── Allowed resource? ✅
          │
          ▼
      Private S3
```

CloudFront serves the file.

---

# 4. Why is it called "signed"?

Because your trusted application creates a **cryptographic signature** for the request.

Conceptually:

```
Resource
   +
Expiration
   +
Policy
   ↓
Private key
   ↓
Signature
```

CloudFront validates that signature using the corresponding public key.

So the user can't simply modify:

```
Expires=10 minutes
```

to:

```
Expires=10 years
```

because the signature would no longer match.

---

# 5. Signed URL example

Imagine an online course website.

You have:

```
S3
├── free-course.mp4
├── premium-course-1.mp4
├── premium-course-2.mp4
└── premium-course-3.mp4
```

Only paid users can access:

```
premium-course-1.mp4
```

Customer purchases the course.

Your application generates:

```
Signed URL
```

valid for:

```
30 minutes
```

Customer watches:

```
CloudFront
    ↓
premium-course-1.mp4
```

After 30 minutes:

```
Signed URL
   ↓
Expired ❌
```

The customer must obtain a new authorized URL.

---

# 6. When is Signed URL useful?

Think:

> **I want to give access to ONE specific object/resource.**
> 

Examples:

- Private video
- Private PDF
- Paid image
- Software download
- Premium document
- Temporary download

For example:

```
/download/invoice-123.pdf
```

You generate a signed URL specifically for that resource.

---

# 7. Now Signed Cookie

A **CloudFront Signed Cookie** works differently.

Instead of putting authorization information directly in the URL, CloudFront uses **cookies sent with requests**.

Conceptually:

```
User
 │
 │ Signed Cookie
 ▼
CloudFront
 │
 ▼
Private content
```

The URL can remain clean:

```
https://cdn.example.com/videos/course1/lesson1.mp4
```

The authorization information is carried in the cookie.

---

# 8. Why would we need a Signed Cookie?

Imagine your customer buys an entire course.

The course has:

```
course/
├── lesson1.mp4
├── lesson2.mp4
├── lesson3.mp4
├── lesson4.mp4
├── images/
├── subtitles/
└── PDFs/
```

You don't want to generate a separate signed URL for every file.

Instead:

```
Customer buys course
        ↓
Backend gives Signed Cookie
        ↓
Customer accesses many files
```

Now:

```
https://cdn.example.com/course/lesson1.mp4
https://cdn.example.com/course/lesson2.mp4
https://cdn.example.com/course/lesson3.mp4
https://cdn.example.com/course/images/slide1.jpg
```

The browser automatically sends the signed cookie with requests.

CloudFront checks it.

---

# 9. Signed Cookie example

Suppose Netflix-like service has:

```
/premium/*
```

A user subscribes.

Your application authenticates them:

```
User
 ↓
Login
 ↓
Subscription valid? ✅
```

Your backend gives them a CloudFront signed cookie.

Then they can request:

```
/premium/movie1.mp4
/premium/movie2.mp4
/premium/movie3.mp4
/premium/poster.jpg
/premium/subtitles.vtt
```

CloudFront validates the cookie for each request.

# 10. The major difference

This is the part you should memorize for SAA-C03.

### Signed URL

> **Authorization information is attached to the URL.**
> 

```
URL
 ↓
Signature
 ↓
Specific resource
```

### Signed Cookie

> **Authorization information is stored in cookies.**
> 

```
Browser
 ↓
Signed Cookie
 ↓
Multiple resources
```

# 12. Comparison table

|  | Signed URL | Signed Cookie |
| --- | --- | --- |
| Authorization stored in | URL | Cookie |
| Best for | **Individual files/resources** | **Multiple files/resources** |
| URL changes? | Yes | No |
| Good for many objects? | Less convenient | ✅ Yes |
| Browser cookie required? | ❌ | ✅ |
| Temporary access | ✅ | ✅ |
| CloudFront private content | ✅ | ✅ |

# Signed URL vs Signed Cookie

This is extremely important for SAA-C03.

| Feature | Signed URL | Signed Cookie |
| --- | --- | --- |
| Access private CloudFront content | ✅ | ✅ |
| Good for individual files | ⭐⭐⭐ | ⭐ |
| Good for multiple files | ⭐ | ⭐⭐⭐ |
| URL changes | Usually yes | **No** |
| Authorization information | URL query parameters | Cookie |
| Browser automatically sends it | No | **Yes** |
| Useful for existing URLs | Less suitable | **Excellent** |
| Typical use | Specific object | Multiple restricted objects |

# 13. This is VERY important for your previous AWS question

Your earlier question said:

> "provide access to multiple private media files only to paying subscribers **without having to change the current URLs**."
> 

Look at the clues:

### "multiple private media files"

and:

### "without changing current URLs"

That strongly points to:

# ✅ Signed Cookies

Because:

```
Signed URL
```

would require changing the URL by adding the signature.

Whereas:

```
Signed Cookie
```

allows the URLs to remain:

```
https://cdn.example.com/video1.mp4
https://cdn.example.com/video2.mp4
https://cdn.example.com/video3.mp4
```

while authorization is carried separately in the cookie.

---

# 14. Visualize the difference

### Signed URL

```
Customer
   │
   │ https://cdn.com/video.mp4
   │ ?Expires=...
   │ &Signature=...
   ▼
CloudFront
   │
   ▼
Private S3
```

### Signed Cookie

```
Customer
   │
   │ URL:
   │ https://cdn.com/video.mp4
   │
   │ Cookie:
   │ CloudFront-Policy=...
   │ CloudFront-Signature=...
   ▼
CloudFront
   │
   ▼
Private S3
```

Notice:

**Signed URL → authorization travels in URL**

**Signed Cookie → authorization travels in cookie**

---

# 15. What happens if the user shares a Signed URL?

Suppose:

```
https://cdn.example.com/movie.mp4
?Expires=...
&Signature=...
```

The user can potentially share that URL with someone else.

If it hasn't expired and the policy allows it, the other person may be able to use it.

That's why expiration and policy restrictions are important.

---

# 16. What happens with Signed Cookies?

The cookie is associated with the user's browser/session.

So another person doesn't automatically receive the cookie simply because they know the clean URL.

However, signed cookies are **not a magic anti-sharing mechanism**; if the cookie itself is stolen, it can potentially be used until it expires or is otherwise invalidated.

---

# 17. Signed URL vs Signed Cookie — exam decision

When reading an SAA question, ask:

### Question says:

> "Access to a single file"
> 

Think:

**Signed URL**

---

### Question says:

> "Access to multiple files"
> 

Think:

**Signed Cookie**

---

### Question says:

> "Don't change existing URLs"
> 

Think:

🔥 **Signed Cookie**

---

### Question says:

> "Give a user temporary access to a specific download"
> 

Think:

🔥 **Signed URL**

---

# 18. One more important concept: they're for private CloudFront content

Typical architecture:

```
                  User
                    │
                    ▼
               CloudFront
              /          \
             /            \
      Signed URL       Signed Cookie
             \            /
              \          /
               ▼        ▼
             Private S3
```

The S3 bucket should be configured so users can't simply bypass CloudFront and access the objects directly.

The goal is:

```
User → CloudFront → S3
```

rather than:

```
User → S3 ❌
```

# 🧠 Final SAA-C03 Cheat Sheet

### 🔗 Signed URL

> **One/few specific resources → authorization in URL**
> 

Example:

```
Download private report.pdf
       ↓
Signed URL
       ↓
CloudFront
```

### 🍪 Signed Cookie

> **Many private resources → authorization in cookie**
> 

Example:

```
Paid subscriber
       ↓
Signed Cookie
       ↓
Access 100 videos/files
       ↓
CloudFront
```

### 🔥 Memorize this:

> **Signed URL = "Here is your special URL."**
> 

> **Signed Cookie = "Here is your access permission; keep using the normal URLs."**
> 

And the strongest SAA clue:

> **Multiple private CloudFront objects + existing URLs must not change → Signed Cookie.**
>
