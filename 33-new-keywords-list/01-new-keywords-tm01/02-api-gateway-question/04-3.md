# 3

Yes — **you absolutely can build and run an application without API Gateway.** That's actually the key point.

If you already have:

```
Frontend
   │
   │ API call
   ▼
Your Backend API
   │
   ▼
Database
```

your application can work perfectly well.

So the question isn't:

> "Can I build an API without API Gateway?"
> 

**Yes, you can.**

The real question is:

> **"When does API Gateway become useful enough to justify putting it in front of my API?"**
> 

That's where the value is.

---

# 1. First, remove one misconception

Suppose you write a Node.js backend:

```
app.get("/products", ...)
app.post("/orders", ...)
```

You deploy it on an EC2 instance:

```
Internet
    │
    ▼
EC2
┌──────────────────┐
│ Node.js          │
│                  │
│ GET /products    │
│ POST /orders     │
│ GET /orders      │
└──────────────────┘
```

Your frontend can call:

```
https://api.myshop.com/products
```

**Nothing is wrong with this.**

You don't *need* API Gateway.

---

# 2. So why does AWS API Gateway exist?

Because as your system becomes more complicated, you start asking:

> "Who is going to handle all the stuff around my APIs?"
> 

For example:

- Who controls who can access my APIs?
- Who limits abusive clients?
- Who handles API keys?
- Who manages different API versions?
- Who handles canary releases?
- Who provides centralized API monitoring?
- Who routes different API paths to different backend services?
- Who handles these things without me building them myself?

You **can build many of these yourself**.

But then you're building an API management layer.

That's where API Gateway becomes useful.

---

# 3. The core idea

Think about the difference like this:

### Without API Gateway

You build:

```
                    YOUR RESPONSIBILITY

Internet
   │
   ▼
Your API server
   │
   ├── Authentication
   ├── Authorization
   ├── Rate limiting
   ├── Routing
   ├── API versioning
   ├── Monitoring
   ├── Logging
   ├── DDoS/security considerations
   └── Business logic
```

Your backend may end up doing **everything**.

---

### With API Gateway

You separate responsibilities:

```
Internet
   │
   ▼
┌──────────────────────────┐
│      API GATEWAY         │
│                          │
│ Authentication           │
│ Authorization            │
│ Throttling               │
│ API keys/usage plans     │
│ Routing                  │
│ Monitoring               │
│ Canary deployment        │
│ API management           │
└────────────┬─────────────┘
             │
             ▼
      YOUR APPLICATION
             │
       Business Logic
             │
             ▼
          Database
```

That's the fundamental reason.

> **API Gateway separates API management concerns from your application's business logic.**
>

```
MyShop
```

You have:

# 5. Then your company grows

Now you have:

```
Web frontend
Mobile app
Admin dashboard
Partner applications
Third-party integrations
```

All of them call your APIs.

```
Web ──────────────┐
                  │
Mobile ───────────┤
                  │

                  ▼
             Your API
                  │
                  ▼
               Backend
```

Now you might want:

```
Web → /products
Mobile → /products
Admin → /admin/*
Partner → /partner/*
```

And you want consistent policies around all of them.

This is where a dedicated API management layer starts becoming valuable.

---

# 6. Example #1 — Authentication

Imagine:

```
GET /orders
```

Only logged-in customers should access it.

Without API Gateway:

```
Frontend
    │
    ▼
Your backend
    │
    ├── Is token valid?
    ├── Is user authenticated?
    ├── Is token expired?
    ├── Is user allowed?
    └── Continue...
```

You write this logic.

That's totally possible.

But with API Gateway:

```
Frontend
    │
    ▼
API Gateway
    │
    ├── Authentication/authorization
    │
    │   ❌ invalid → reject
    │
    │   ✅ valid
    ▼
Backend
```

Your backend can focus more on:

> "What should I do with this order?"
> 

rather than handling every API-entry concern itself.

---

# 7. Example #2 — Rate limiting

This is one of the easiest ways to understand API Gateway.

Suppose your API can comfortably handle:

```
1,000 requests/second
```

But someone sends:

```
100,000 requests/second
```

Without a gateway:

```
Internet
   │
   │ 100,000 req/s
   ▼
Your backend
   💥
```

You can build rate limiting yourself.

For example:

```
if requests > 1000/sec:
    reject
```

But now **you have to implement, maintain, test, and scale that system.**

API Gateway provides managed throttling controls.

Conceptually:

```
Internet
   │
   │ 100,000 requests
   ▼
API Gateway
   │
   ├── Allowed traffic → Backend
   │
   └── Excess → throttled
```

That's useful.

---

# 8. Example #3 — You have multiple backends

Imagine your company has moved toward microservices.

Now:

```
/products
      ↓
Product Service

/orders
      ↓
Order Service

/payments
      ↓
Payment Service

/users
      ↓
User Service
```

Without a gateway, your frontend might need to know:

```
product-api.company.com
order-api.company.com
payment-api.company.com
user-api.company.com
```

That's messy.

Instead:

```
                 api.company.com
                       │
                       ▼
                 API Gateway
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    /products       /orders       /payments
        │              │              │
        ▼              ▼              ▼
     Product         Order         Payment
     Service         Service        Service
```

Now the client has **one API entry point**.

That's a major architectural benefit.

The client doesn't necessarily need to know what's behind the API Gateway.

That's an abstraction layer.

# 10. Example #5 — Canary deployment

This connects directly to the question you asked earlier.

Suppose:

```
API v1
```

is currently running.

You create:

```
API v2
```

Without a gateway, you might need to implement traffic splitting using other infrastructure.

With API Gateway's REST API canary capability, you can conceptually have:

```
                 API Gateway
                     │
              Production stage
                     │
              ┌──────┴──────┐
              │             │
             95%            5%
              │             │
              ▼             ▼
             v1            v2
```

Then:

```
95/5
 ↓
90/10
 ↓
75/25
 ↓
50/50
 ↓
0/100
```

That's exactly why API Gateway was relevant in your previous question.

---

# 11. Example #6 — API keys and usage control

Imagine you have partners using your API.

```
Partner A
Partner B
Partner C
```

You might want:

```
Partner A → 10,000 requests/day
Partner B → 50,000 requests/day
Partner C → 100,000 requests/day
```

You can build your own system for this.

Or you can use API management capabilities such as API keys and usage plans where applicable.

Conceptually:

```
Partner
   │
   │ API request + API key
   ▼
API Gateway
   │
   ├── Identify client
   ├── Apply usage limits
   ├── Apply throttling
   ▼
Backend
```

Again:

**You don't have to build all this yourself.**

# 12. Here's the BIGGEST distinction

You might be thinking:

> "But I can write all these things myself."
> 

### Correct.

You can.

That's why API Gateway isn't mandatory.

The real comparison is:

```
OPTION A

Build everything yourself
        ↓
More control
        ↓
More engineering responsibility
```

versus:

```
OPTION B

Use managed API Gateway capabilities
        ↓
Less infrastructure to build/manage
        ↓
AWS handles many API-management concerns
```

# 13. Think about it like Kubernetes

You already know Kubernetes, so here's an analogy.

You can run:

```
Docker container
```

without Kubernetes.

Absolutely.

You don't **need** Kubernetes to run containers.

But why does Kubernetes exist?

Because when you have:

- many containers
- scaling
- service discovery
- rolling deployments
- health checks
- orchestration
- self-healing

you don't want to manually implement everything.

Same fundamental idea.

### Docker vs Kubernetes

```
Docker
   ↓
Run containers
```

```
Kubernetes
   ↓
Manage containers at scale
```

Similarly:

```
Your backend
   ↓
Can expose APIs directly
```

```
API Gateway
   ↓
Manage/expose/control APIs at scale
```

It's not a perfect 1:1 comparison, but it's a useful mental model.

# 14. API Gateway is NOT a replacement for your backend

This is crucial.

Don't think:

```
API Gateway = Backend ❌
```

Instead:

```
API Gateway ≠ Business Logic
```

Think:

```
              API Gateway
                   │
           "Can this request
            enter? Where does
            it go? How much
            traffic is allowed?"
                   │
                   ▼
              Backend
                   │
           "What should the
            application actually
            do?"
```

For example:

### API Gateway

```
GET /products
     ↓
Is request allowed?
     ↓
Where should it go?
     ↓
Forward request
```

### Backend

```
Get products
     ↓
Query database
     ↓
Apply business rules
     ↓
Return products
```

# 15. So when DON'T you need API Gateway?

This is also important for your real-world architecture knowledge.

Suppose you have:

```
Small application

React
  ↓
Node.js
  ↓
PostgreSQL
```

Maybe:

- One backend
- Low traffic
- Simple authentication
- No complicated API management
- No multiple services
- No need for API-specific throttling/keys
- You already have a suitable load balancer/reverse proxy

Then:

**Don't automatically add API Gateway just because you're using AWS.**

It can introduce additional cost and architectural complexity.

You might simply use:

```
Internet
   ↓
ALB
   ↓
EC2/ECS
   ↓
Backend
```

That's completely valid.

---

# 16. When should you seriously consider API Gateway?

Think about API Gateway when you start saying:

> "I need a managed front door specifically for APIs."
> 

Especially when you need several of these:

```
☑ API authentication/authorization
☑ API keys / usage controls
☑ API throttling
☑ API-specific monitoring
☑ Multiple API versions/stages
☑ Canary API deployments
☑ Central API routing
☑ Multiple backend services
☑ Lambda/serverless API integration
☑ A stable API endpoint hiding backend implementation
```

# 🎯 The one sentence to remember

> **You don't need API Gateway to create or expose an API. You use API Gateway when you want a managed, centralized front door to control, secure, throttle, route, monitor, and deploy APIs without having to build and maintain all those API-management capabilities yourself.**
> 

And for **your SAA-C03 question**, the clue is even stronger:

> **API Gateway already provides native canary deployment for REST APIs, so instead of creating another API Gateway or manually replacing the existing API, you can deploy the new version as a canary and gradually shift traffic.**
> 

That's why **Option 3** is the best answer.
