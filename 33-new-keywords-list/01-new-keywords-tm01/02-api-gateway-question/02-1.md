# 1. First: What is an API?

API stands for **Application Programming Interface**.

Don't think of API as some mysterious AWS technology.

Think of an API as a **controlled communication door** between applications.

### Real-life analogy: restaurant 🍔

Imagine you go to a restaurant.

There are three important parts:

```
YOU
 │
 │ "I want a burger"
 ▼
WAITER
 │
 │ Takes your request to kitchen
 ▼
KITCHEN
 │
 │ Prepares burger
 ▼
WAITER
 │
 │ Brings result
 ▼
YOU
```

You don't walk into the kitchen yourself.

The **waiter is like an API**.

You say:

> "Give me my order."
> 

The waiter takes that request to the appropriate place and brings the response back.

# 4. So what exactly is an API?

An API defines **how another application can communicate with your application**.

For example:

```
GET    /products
GET    /products/101
POST   /orders
GET    /orders/500
DELETE /cart/101
```

These are API endpoints.

Think of an endpoint as a **specific door**.

```
api.myshop.com
       │
       ├── GET /products
       ├── GET /products/101
       ├── POST /orders
       ├── GET /orders/500
       └── DELETE /cart/101
```

Each door does something different.

# 5. API request and response

This is one of the most important concepts for you.

### Request

Frontend says:

```
GET /products/101
```

Meaning:

> "Give me product number 101."
> 

Backend processes it.

### Response

Backend says:

```
{
  "id":101,
  "name":"Laptop",
  "price":1200
}
```

So:

```
CLIENT
  │
  │ HTTP Request
  │ GET /products/101
  ▼
SERVER
  │
  │ HTTP Response
  │ 200 OK
  │ { product data }
  ▼
CLIENT
```

That's an API call.

# 6. What does GET, POST, PUT, DELETE mean?

You'll see these constantly.

| Method | Meaning | Example |
| --- | --- | --- |
| GET | Read data | Get products |
| POST | Create something | Create an order |
| PUT/PATCH | Update something | Update address |
| DELETE | Remove something | Delete cart item |

For example:

```
GET /products
```

→ Give me products.

```
POST /orders
```

→ Create an order.

```
DELETE /cart/123
```

→ Remove item 123 from cart.

# 8. API Gateway is basically the front door to your APIs

Think:

```
                 INTERNET
                    │
                    ▼
           ┌─────────────────┐
           │  API GATEWAY    │
           │                 │
           │ Authentication  │
           │ Authorization   │
           │ Throttling      │
           │ Monitoring      │
           │ Routing         │
           │ Canary          │
           └────────┬────────┘
                    │
                    ▼
               YOUR BACKEND
```

Your frontend doesn't necessarily need to talk directly to your backend.

Instead:

```
Frontend
    │
    │ HTTPS request
    ▼
API Gateway
    │
    │ forwards request
    ▼
Backend
    │
    ▼
Database
```

---

# 9. Very important: API Gateway does NOT necessarily contain your backend

This is a common beginner misunderstanding.

API Gateway is **not your application backend**.

It's more like a **traffic controller / front door**.

For example:

```
                  API GATEWAY
                       │
           ┌───────────┼────────────┐
           ▼           ▼            ▼
        Lambda       ECS/EC2      Other service
           │           │
           ▼           ▼
        Database    Database
```

API Gateway can integrate with different backend services.

# 12. Where does API Gateway help?

This is the important part.

API Gateway can provide a managed API entry layer for things such as:

### 1. Routing

For example:

```
/products → Product backend

/orders → Order backend

/users → User backend
```

### 2. Authentication/authorization

You can control who can call APIs.

### 3. Throttling

Suppose someone sends an enormous number of requests.

API Gateway can limit request rates.

```
Client
   │
   │ 10000 requests/sec
   ▼
API Gateway
   │
   ├── Allowed requests → Backend
   │
   └── Excess requests → throttled
```

### 4. Monitoring/logging

You can integrate with AWS monitoring services to observe API activity.

### 5. Custom domain

Instead of users seeing an AWS-generated hostname, you can have:

```
api.myshop.com
```

### 6. Deployment stages

You can have:

```
dev
test
prod
```

### 7. Canary releases

This is particularly important for **your question**.

# 13. Now let's understand API Gateway stages

Suppose your API has:

```
GET /products
POST /orders
GET /orders/{id}
```

You might have:

```
API Gateway
     │
     ├── dev
     ├── test
     └── prod
```

A **stage** represents a lifecycle environment/version of the deployed API. AWS describes a stage as a named reference to a deployment, and the deployment is effectively a snapshot of the API configuration.

For example:

```
dev
 ↓
Developer testing

test
 ↓
QA testing

prod
 ↓
Real customers
```

---

# 14. What is a Deployment?

This is another key concept.

Suppose you have:

```
API v1
```

You make changes:

```
API v2
```

In API Gateway REST APIs, changing the API doesn't automatically make that changed configuration available through the deployed stage. You need to create a new deployment and associate it with a stage.

Think:

```
API definition
     │
     │ Deploy
     ▼
Deployment
     │
     ▼
Stage
     │
     ▼
Users
```

A deployment is essentially a **snapshot**.

# 17. What does the Route 53 part mean?

The question says:

> "API Gateway endpoint is accessed through a custom domain name set up with an Amazon Route 53 alias record."
> 

Let's break that down.

Instead of customers calling something like:

```
https://abc123.execute-api.region.amazonaws.com/prod
```

you can give customers a friendly domain:

```
https://api.myshop.com
```

Route 53 DNS can use an alias record to route the domain toward an API Gateway endpoint.

Conceptually:

```
Customer
   │
   │ https://api.myshop.com/products
   ▼
Route 53
   │
   │ DNS resolution
   ▼
API Gateway
   │
   ▼
Backend
```

### VERY IMPORTANT

Route 53 is **not doing the API deployment** here.

It's primarily helping the domain name resolve to the API Gateway endpoint.
