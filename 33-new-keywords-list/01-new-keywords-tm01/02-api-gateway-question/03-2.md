# 18. Why does the question mention the custom domain?

Because the company wants to update the API **without disrupting customers**.

Customers already know:

```
api.myshop.com
```

You don't want to suddenly tell everyone:

> "Please change your application to a completely different URL."
> 

The goal is:

```
Customer
    │
    │ SAME
    ▼
api.myshop.com
    │
    ▼
API Gateway
    │
    ▼
new API version
```

The custom domain stays stable.

# 19. Now the MOST important part: API Gateway Canary

AWS API Gateway REST APIs have a built-in **canary release deployment** capability.

AWS describes it as keeping the base production release on the stage while attaching a canary release containing the new version to that same stage. Traffic is divided according to a configured percentage.

This is perfect for the question.

Suppose production currently has:

```
API Gateway
     │
     ▼
prod stage
     │
     ▼
API v1
```

100% of customers use v1.

Now you deploy v2 as the canary.

```
                   API Gateway
                       │
                   prod stage
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
          Production         Canary
            v1                v2
            95%                5%
```

Now:

```
95% customers → v1
5% customers  → v2
```

API Gateway supports a configurable `percentTraffic` value for the canary deployment.

---

# 20. Why is this so powerful?

Imagine:

```
1,000,000 API requests
```

Instead of:

```
1,000,000 → v2
```

you might initially have:

```
950,000 → v1
50,000   → v2
```

Then monitor v2.

Maybe:

```
Error rate
Latency
Application logs
API metrics
Backend health
```

If v2 is healthy:

```
95% v1
5%  v2

      ↓

90% v1
10% v2

      ↓

75% v1
25% v2

      ↓

50% v1
50% v2

      ↓

0% v1
100% v2
```

That's Canary.

---

# 21. What happens if v2 is broken?

Suppose:

```
v1 → 95%
v2 → 5%
```

You discover:

```
v2 → ERROR RATE HIGH ❌
```

You stop the canary / return traffic to the production version.

Conceptually:

```
v1 → 100%
v2 → 0%
```

Most customers never experienced the problematic version.

That's why canary is excellent for **reducing blast radius**.

### Why it sounds reasonable

You're thinking:

```

       ↓
New API Gateway
       ↓
New API version
```

And you want the same domain:

```
api.myshop.com
```

But this is not the best answer.

### Why?

The question asks for:

> **MINIMAL data loss**
> 

and:

> **MOST cost-effective**
> 

Creating an entirely new API Gateway isn't necessary.

You already have an API Gateway capable of handling deployment/version management and canary release.

You're introducing an unnecessary additional API Gateway.

Conceptually:

```
Existing API Gateway
        ↓
Canary capability already available

Instead of using it...

Create another API Gateway ❌
```

More infrastructure/management is unnecessary.

### Exam lesson

If AWS already provides a native feature that directly solves the requirement, don't create additional infrastructure unless the question requires it.

# ❌ Option 2 — Blue-Green

> Implement a blue-green deployment strategy for API Gateway...
> 

This is a very tempting answer because you just learned Blue-Green.

But look carefully at the question.

The requirement is:

> **MINIMAL data loss**
> 

and:

> **MOST cost-effective**
> 

and it's specifically about **Amazon API Gateway**.

Blue-Green would conceptually look like:

```
API Gateway

     ├── BLUE → v1
     │
     └── GREEN → v2
```

Then:

```
100% → Blue

       ↓ switch

100% → Green
```

The problem is that you're maintaining another full environment/version path and switching traffic.

The question specifically describes an API Gateway deployment scenario where API Gateway's **native canary release** is designed to send a controlled percentage of traffic to the new version while the existing version remains the production release.

So Blue-Green isn't the best fit.

---

# ✅ Option 3 — Canary

> Implement a canary release deployment strategy for the API Gateway.
> 

**THIS IS THE CORRECT ANSWER.**

Why?

Because API Gateway REST APIs directly support canary deployments.

You can:

```
Existing production version
        │
        │ remains production
        ▼
       v1

New version
        │
        │ canary
        ▼
       v2
```

Then:

```
v1 → 95%
v2 → 5%
```

Monitor.

Then:

```
v1 → 90%
v2 → 10%
```

Monitor.

And continue until:

```
v1 → 0%
v2 → 100%
```

AWS explicitly documents that API Gateway canary deployments split traffic between the production and canary releases according to a configured ratio, allowing the new API version to be tested while the base version remains in production.

### Why does this minimize disruption?

Because only a small percentage of requests initially reach v2.

### Why is it cost-effective?

Because you're using API Gateway's **built-in canary deployment capability**, rather than creating a separate API Gateway environment.

### Why minimal data loss?

The old production version continues serving the majority of requests while the new version is validated gradually.

**Therefore: Option 3.**

# ❌ Option 4

> Modify the existing API Gateway with the updated version using import-to-update in overwrite or merge mode.
> 

This one is tricky.

Because the question says:

> OpenAPI JSON or YAML
> 

and API Gateway absolutely supports importing OpenAPI definitions and using **merge or overwrite** modes.

So this is a **real API Gateway feature**.

But it does **not solve the deployment strategy requirement as well as canary**.

You're basically doing:

```
     ↓
Import new API definition
     ↓
Update existing API
```

Whereas the desired approach is:

```
Current production version
          +
New version
          ↓
Canary traffic
          ↓
Monitor
          ↓
Gradually promote
```

The question is specifically asking how to reduce disruption and safely introduce the new version.

**Import/merge/overwrite is an API definition management mechanism, not the native gradual traffic-shifting strategy being asked for.**

# 24. OpenAPI — why does it appear in the question?

You may wonder:

> "What is OpenAPI JSON/YAML?"
> 

Think of OpenAPI as a **description/blueprint of your API**.

For example:

```
API:
  /products
      GET

  /orders
      POST

  /orders/{id}
      GET
```

You can describe these API definitions in an OpenAPI document.

API Gateway can import OpenAPI definitions and can use them to create or update APIs. AWS supports OpenAPI 2.0 and 3.0 definitions for REST APIs, subject to documented exceptions.

So:

```
OpenAPI file
     │
     │ import
     ▼
API Gateway
```

But:

```
OpenAPI import
```

is NOT synonymous with:

```
Canary deployment
```

That's a critical exam distinction.

# 26. One subtle point about "data loss"

Be careful with the wording.

**Canary deployment itself does not magically prevent database data loss.**

That's an important architectural distinction.

Canary primarily reduces **customer/request impact and deployment blast radius**.

If v1 and v2 write to the same database and v2 has a bad database migration, you can still have data problems.

For a real production system, you'd also think about:

```
Database compatibility
Backward-compatible schema changes
Transactions
Backups
Migration strategy
Idempotency
Rollback strategy
```

So when the exam says "minimal data loss" in this scenario, understand it primarily as **minimizing disruption/risk during the API version rollout**, not that API Gateway itself provides database backup or data recovery.
