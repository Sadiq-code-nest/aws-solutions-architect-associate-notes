# A

### Step 1 — Access Logs answer the request-level question

The requirement isn't merely:

> "How many requests happened?"
> 

It wants:

> **"Give me detailed information about the HTTP requests."**
> 

ALB access logs are designed for exactly this.

Conceptually:

```
Request
   ↓
ALB
   ↓
Access Log
   ↓
Request details
 ├── Client IP
 ├── Request
 ├── Status
 ├── Timing
 └── Response information
```

---

### Step 2 — Client IP is available

The question explicitly says:

> **"client's IP address"**
> 

ALB access logs include the source/client IP information.

That's a strong clue toward **access logs**.

---

### Step 3 — Latency information is available

Access logs contain timing information that can be used to investigate request latency.

This is different from simply looking at an ALB CloudWatch metric.

```
CloudWatch metric:
"Average latency = X"

Access log:
"THIS request from THIS client took X seconds"
```

The second is much more useful for detailed troubleshooting.

---

### Step 4 — Application Insights handles application troubleshooting

The question also mentions:

> **"analyzing traffic patterns and ... troubleshooting Docker applications"**
> 

CloudWatch Application Insights helps monitor application resources and detect problems across the application stack.

So the two pieces complement each other:

```
ALB Access Logs
      ↓
Detailed request-level information

CloudWatch Application Insights
      ↓
Application monitoring + troubleshooting
```

---

### Step 5 — Health checks are separate

The question deliberately says:

> **"load balancer’s availability is monitored separately through the ELB health check."**
> 

This tells you:

**Don't choose a solution merely because it monitors ALB health.**

The missing requirement is **request-level information**.

            **Application Insights** automatically helps you **monitor applications and detect common problems**, especially enterprise applications such as **Microsoft SQL Server, .NET, SAP, and other supported workloads**.
