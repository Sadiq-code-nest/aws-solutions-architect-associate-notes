# Sticky Sessions (Session Affinity) — AWS SAA-C03

**Sticky Sessions** means the load balancer tries to send requests from the **same client to the same backend instance** for a period of time.

Normally:

```
Client
  │
  ▼
Load Balancer
  ├── EC2-A
  ├── EC2-B
  └── EC2-C
```

Without stickiness, Client 1 might go:

```
Request 1 → EC2-A
Request 2 → EC2-C
Request 3 → EC2-B
```

With stickiness:

```
Client 1
   │
   ▼
Load Balancer
   │
   └──────────────► EC2-A
                    ↑
              same client
```

So subsequent requests from that client are directed to the **same target**, as long as the sticky session is valid and the target remains available.

---

## Why Use Sticky Sessions?

Suppose an application stores a user's session data locally on an EC2 instance:

```
User Login
    ↓
EC2-A
    ↓
Session data stored locally
```

If the next request goes to EC2-B:

```
User
 ↓
Load Balancer
 ↓
EC2-B
 ↓
❌ Session data not found
```

The user may appear logged out or lose application state.

With sticky sessions:

```
User
 ↓
Load Balancer
 ↓
EC2-A
 ↓
Session data available ✅
```

### Typical use case

> An application stores session information locally on backend EC2 instances and cannot easily use a shared session store.
> 

---

# Which Load Balancers Support Stickiness?

| Load Balancer | Sticky Sessions |
| --- | --- |
| **Classic Load Balancer (CLB)** | ✅ |
| **Application Load Balancer (ALB)** | ✅ |
| **Network Load Balancer (NLB)** | ✅ |
| Gateway Load Balancer | ❌ Not the typical application sticky-session feature |

**Exam clue:** If the question says **"same client → same EC2 instance"**, think **Sticky Sessions**.

---

# Cookie Types — Important for SAA-C03

There are two major approaches you'll encounter with **ALB/CLB**:

| Type | Generated by | Cookie | Main idea |
| --- | --- | --- | --- |
| **Duration-based cookie** | Load balancer | **ALB:** `AWSALB` | LB maintains stickiness for configured duration |
| **Application-based cookie** | Application/target | Custom cookie | Application controls the session cookie |
| **Application cookie generated by ALB** | Load balancer | **`AWSALBAPP`** | ALB-specific application-cookie mechanism |

### ⚠️ Reserved cookie names

For custom application cookies, don't use:

```
AWSALB
AWSALBAPP
AWSALBTG
```

These names are reserved by Elastic Load Balancing.

---

# Duration-Based Stickiness

The load balancer generates the cookie.

For ALB:

```
AWSALB
```

For CLB:

```
AWSELB
```

Example:

```
Client
  │
  │ Request
  ▼
ALB
  │
  ▼
EC2-A
  │
  └── ALB gives client AWSALB cookie
```

Next request:

```
Client
  │
  │ AWSALB cookie
  ▼
ALB
  │
  └──────► EC2-A
```

The cookie has an **expiration duration** that you configure.

---

# Application-Based Cookies

The application/target generates the cookie.

Example:

```
Client
   ↓
ALB
   ↓
EC2-A
   ↓
Application creates session cookie
```

The cookie can contain application-specific information/attributes.

### Important

The custom cookie name is configured **for the target group**.

Example:

```
mySessionCookie
```

But don't use:

```
AWSALB
AWSALBAPP
AWSALBTG
```

because those are reserved.

---

# Master Comparison

| Feature | Duration-Based | Application-Based |
| --- | --- | --- |
| Cookie generated by | Load Balancer | Application/target |
| ALB cookie | `AWSALB` | Custom application cookie / `AWSALBAPP` mechanism |
| CLB cookie | `AWSELB` | Application cookie |
| Expiration | Configurable | Controlled according to application mechanism |
| Application controls cookie | ❌ | ✅ |
| Useful when | Simple session affinity | Application needs custom session information |
| Main purpose | Keep client on same target | Keep client on same target |

---

# ⚠️ Biggest Disadvantage of Sticky Sessions

Sticky sessions can cause **uneven load distribution**.

Example:

```
100 users

        ALB
         │
   ┌─────┼─────┐
   ↓     ↓     ↓
 EC2-A EC2-B EC2-C
  70     20    10
```

Because users are tied to particular instances, the load balancer cannot freely distribute every request.

So:

> **Stickiness improves session continuity but can reduce load-balancing efficiency.**
> 

---

# Sticky Sessions vs Stateless Architecture

| Sticky Sessions | Stateless Application |
| --- | --- |
| Client tends to stay with same instance | Requests can go to any instance |
| Session may be stored locally | Session stored externally/shared |
| Can create uneven load | Better load distribution |
| Easier for legacy applications | Better for modern scalable applications |
| Can complicate scaling/failover | Easier horizontal scaling |

A better modern architecture is often:

```
Client
   ↓
ALB
   ↓
EC2 / ECS
   ↓
ElastiCache / DynamoDB
   ↓
Shared session state
```

Then any backend instance can handle the request.

# 🧠 SAA-C03 Exam Clues

| Question says... | Think... |
| --- | --- |
| **Same user → same EC2 instance** | ⭐ Sticky Sessions |
| **Session data stored locally on EC2** | Sticky Sessions may be needed |
| **User loses session after requests go to different instances** | Sticky Sessions or external session store |
| **Cookie-based session affinity** | Sticky Sessions |
| **ALB cookie `AWSALB`** | Duration-based stickiness |
| **CLB cookie `AWSELB`** | Duration-based stickiness |
| **Custom application cookie** | Application-based stickiness |
| **Uneven load across instances** | ⚠️ Sticky Sessions can cause this |
| **Need maximum scalability and even distribution** | Prefer stateless architecture |
| **Same client always goes to same target** | Sticky Sessions |

### 🔥 One-line memory

> **Sticky Session = "Same client, same backend target" using cookies/session affinity — but it can cause uneven load.**
>
